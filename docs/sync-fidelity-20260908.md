# 2026-09-08 同步顺序与文案稳定性

## 已实现

- 抖音按官方分类列表和请求游标串联分页，不按响应完成时间排名，不从全页推荐内容猜收藏/喜欢。
- B站喜欢保留官方分页顺序；收藏先读取各收藏夹首屏，再按真实收藏时间归并。
- 默认列表使用来源快照与来源排名；文案完成、后台刷新、旧请求晚到不改变新排名。
- 50/100 条导入分批全部提交，去重后统一快照、总量和排名偏移；不再只处理前 10 条。
- 只有完整、顺序可靠且无失败的来源快照才能解除旧分类成员关系；保留文案、知识、计划和其他分类。
- 完整文案先保存，再生成摘要；失败重试复用文案，避免重复下载及语音识别。
- 本地元数据优先、短数据库事务、有界任务投递、瞬态网络重试、FFmpeg 双管道排空。

## 验收

- 后端 unittest：本地来源、平台导入、任务检查点、取消、媒体管道、ASR 重试、身份隔离等定向回归。
- 前端 Node 原生测试：来源分类与排序、去重批处理、完整文案准备、多来源同步；TypeScript 全量检查。
- 桌面 `npm run verify:platform-account`：异步分页乱序、跨夹归并、缺页、失效成员、重试边界等。
- 使用现有测试工具，不新增测试框架；外部平台和模型调用在回归中用测试替身，不消耗用户额度。

## 明确边界

- 桌面单次采集仍有 100 条上限；触顶显示限量，不声称已获得全部收藏。旧尾部保留，无法保证未重新读取部分与平台当前状态相同。
- 官方未明确结束、缺少收藏时间、无效成员或部分请求失败均不标成完整可靠。
- 官方空列表目前保守报未读取到作品，不自动清空来源关系；需后续完善空快照授权及对账路径。
- B站多收藏夹合并为最近收藏视图；不同夹的手动内部排序不等于全站合并顺序。
- 本轮未在用户已登录的真实抖音/B站账号逐条对照，也未做真实网络速度提升百分比测试。
- 历史错误顺序需要更新桌面端后重新同步，后端无法从发布时间推回真实收藏顺序。
