## 本次发现与修复

旧客户端窗口可能继续运行缓存的旧网页，绕过新版网页上的原生版本提示。基线接口仅记录 `client_version`，仍接受 1.1.2 声称可信的来源排名。

HTTP 回归先证实：1.1.3 提交 `[A, B]` 后，旧版 1.1.2 用更晚的快照时间提交 `[B, A]`，接口返回 200，已有顺序被改写。改后在创建同步记录、推进快照水位之前检查原生版本，可信排名要求正式数字版本 `>= 1.1.4`。此次原生审查还补了账号上下文保护，因此最终门槛包含该修复，不停留在 1.1.3。

- 收藏、喜欢、作品均拒绝 1.1.2、1.1.3 的可信排名写入，提示升级。
- 缺失、畸形、带预发布后缀的版本不能写可信排名；1.1.4、1.1.10、1.2.0、2.0.0 可正常更新。
- 拒绝请求不写元数据、台账和同步批次，不能用未来水位阻挡有效请求。
- 旧版非可信元数据登记仍兼容，已有可信排名不变，新资料无排名并放在尾部。
- 轻量契约测试核对前端与后端的最低版本常量，防止升级门槛漂移。

版本检查是兼容性保护，不是对客户端能力的密码学认证。

## 边界与结论范围

后端排序水位仍采用采集端提交的时间，当前客户端每次采集创建毫秒时间。若不同内容被人为指定为完全相同的快照时间，双方目前都可写入，原请求重放也可能恢复自身排名；本地 HTTP 已复现。正常的每次采集会生成新时间，这不是本次旧网页回归的原因。不同设备需要合理校准时间；超过服务器时间五分钟的请求会被拒绝，小幅时钟偏差仍可能影响先后判断。此次未扩大为服务端序号/快照协议重构，也未改变 B站合法分批语义。

如果服务进程在批次运行中退出，原幂等请求的 `running` 记录目前没有自动过期接管，相同请求重放会继续返回 409；重新点击同步使用新时间，不受该旧请求幂等键限制。这属于失败恢复的剩余边界，未声称已解决。

本轮没有在真实 PostgreSQL 中执行多进程压力测试。生产短事务的 User 行锁、原子 UPSERT 和提取咨询锁已审阅；本地 SQL/锁契约测试与临时 SQLite 验证不能证明所有生产并发场景。
