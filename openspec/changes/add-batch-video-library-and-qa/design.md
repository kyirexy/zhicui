## Context

知萃目前通过 `/api/extract` 和 `/api/extract/stream` 处理一条公开链接，转录文案、生成 AI 卡片并写入 `notes`。单条笔记已经支持基于完整文案和 AI 结构化理解的有依据问答。

本机另有 `jiji262/douyin-downloader` 的 Web 服务运行在 `127.0.0.1:9000`，可以登录抖音、采集点赞视频、读取 `download_manifest.jsonl` 并通过 `/files/` 提供封面和媒体文件。该服务不属于知萃的生产代码，也不应成为主应用启动的硬依赖。

## Goals / Non-Goals

**Goals:**

- 把下载器中的收藏视频作为一种可选内容来源显示在知萃中。
- 允许用户选择视频后执行完整 ASR、AI 卡片和保存流程。
- 在桌面和移动端提供高密度但可读的视频网格。
- 允许用户基于多条已提取视频的文案进行有来源约束的问答。
- 明确展示 `like`、`collection`、`collect`、`post` 的真实语义，并在知萃内完成扫码登录。
- 提供一次确认后的自动流水线：采集完成后继续提取文案、生成卡片和总结。
- 对几十条视频使用规划、全局检索和可选 map-reduce 的研究型 Agent，而不是平均截断每条文案。
- 保持用户数据隔离、上下文长度边界和现有单条提取兼容性。

**Non-Goals:**

- 不把 `douyin-downloader` 源码复制进知萃后端。
- 不在本次变更中实现生产级队列、分布式任务或断点续传。
- 不把抖音登录 Cookie 写入知萃数据库。
- 不对图集做 OCR 或视觉问答；首版只对存在可播放媒体的视频执行 ASR。
- 不替换现有知识库和单条笔记问答页面。

## Decisions

### 1. 通过 HTTP 适配器连接下载器

新增 `douyin_library` 服务，通过可配置的 `DOUYIN_DOWNLOADER_URL` 调用下载器的健康、作品和采集 API。主应用只接收标准化后的收藏视频 DTO，不读取参考项目内部 Python 对象或数据库。

选择这一方式是因为本地 Web 服务已经形成稳定边界，也可以在未来把下载器部署为独立伴随服务。直接导入参考项目包会把 Cookie、异步下载器和主 FastAPI 生命周期耦合在一起。

### 2. 继续使用 Note 作为已处理视频的来源

下载器条目在未处理时只存在于连接器响应中。用户点击提取后，知萃下载媒体、提取音频、执行 ASR、生成卡片并创建普通 `Note`。来源作者、封面、原始作品链接和来源类型写入 `ai_summary.source_meta`，`Note.to_dict()` 以兼容字段输出。

该方案避免引入只用于缓存外部清单的新表。未处理视频列表随下载器清单变化，已处理结果则继续享受现有用户隔离、知识库和计划能力。

### 3. 单条导入 API，前端编排可观察的自动流水线

后端提供单条下载器视频提取端点。前端对用户选择按顺序调用，并逐条显示处理中、已完成和失败状态。

知萃代理下载器登录与采集任务状态。用户选择来源和数量后，可一次启动“采集 → 刷新清单 → 选择新条目 → 顺序 ASR → 卡片总结”的自动流程。首版仍不引入持久化后台队列；页面明确展示阶段和失败条目，单条接口保持幂等，可重新执行未完成项。

### 4. 直接媒体转录复用现有 ASR 配置

新增直接媒体 URL 转录帮助函数：将下载器 `/files/` 媒体保存到临时目录，通过 FFmpeg 提取音频，优先调用当前运行时 ASR 配置，失败时调用已有本地 ASR 回退。临时文件在成功或失败后都必须清理。

### 5. 多视频问答使用研究型 Agent 构建有限上下文

集合问答最多接受 50 个用户拥有的 `note_id`。服务端先让规划 Agent 把问题拆成检索词、子问题、覆盖方式和回答计划；随后在本地扫描每条完整文案的全部分块，以全局排序和来源多样性选择有限上下文。快速模式执行一次综合，深度模式先按来源批次 map 出带引用的发现，再 reduce 成最终回答。无论模式如何，模型引用都必须逐字存在于对应视频文案或摘要中，否则丢弃。

响应返回 Agent 阶段、扫描视频数、完整文案字符数、扫描分块数、命中来源数和实际进入上下文的来源数。这样“尽可能多读取”指扫描全部来源，而不是把全部原文无边界塞进模型窗口。

### 6. 独立 `/library` 工作台、共享类型切换和按需 AI 分屏

首页与 `/library` 都显示“单条链接 / 批量视频库”切换。`/library` 默认采用全宽响应式 CSS Grid，手机 2 列、平板 3 列、常规桌面 4 列、宽屏最多 5 列。问答不再作为窄侧栏常驻：页面提供一个高辨识度的“向视频问 AI”入口，打开后桌面工作区切换为等宽两列，左侧视频继续可选，右侧问答保持接近视口高度；1023px 以下改为全屏问答层。关闭后立即恢复全宽视频网格，不清空当前选择和问答历史。

### 7. 登录和来源语义由连接器提供、知萃负责说明

知萃后端只代理下载器的扫码启动、扫码状态、Cookie 有效状态和采集 job 状态，不读取或返回 Cookie 明文。前端来源选项固定显示：

- `like`：点过红心的喜欢作品；
- `collection`：当前登录账号的全部收藏作品，包含未加入手动收藏夹的默认收藏；
- `collect`：用户手动建立的收藏夹，作为后续文件夹筛选兼容能力；
- `post`：当前登录账号自己发布的作品。

知萃对外继续使用稳定的 `collect` 来源类型，但在触发采集时把它翻译为下载器的 `collection` 模式；下载器 manifest 中的 `collection` 目录也归一化为知萃的 `collect`。下载器 manifest 没有独立来源字段时，适配器从文件目录段推断 `source_mode`，并允许按模式过滤。

### 8. 用渐进披露降低操作密度

视频库默认层级只保留来源切换、一个主采集按钮、搜索、视频选择和一个明显的问答入口，完整问答面板按需打开。处理数量与自动提取开关放入“采集设置”；研究模式、输出形式与自定义要求放入“回答设置”。未提取卡片不再重复显示大号“提取文案”按钮，用户勾选后由上下文操作栏统一处理。单条删除收进已提取卡片的溢出菜单；开发测试专用的批量重置不进入产品界面。

### 9. 删除知识结果而不删除外部媒体

单条删除必须按 `current_user.id` 限定数据，并先删除关联 Plan，再删除 Note。该操作让视频恢复为“待提文案”，但不调用下载器删除文件，也不修改用户在抖音中的喜欢、收藏夹或作品。

### 10. 问答默认覆盖全部已有文案

问答工作台默认使用当前来源中最多 50 条已有完整文案的视频，用户无需先勾选即可提问。需要缩小研究范围时，用户可切换为“仅勾选视频”；该模式继续忽略尚未生成文案的勾选条目。范围切换会清空与旧来源绑定的对话，避免后续问题错误沿用不同证据集合。

### 11. 有界同步与有限 AI 处理分离

处理设置提供两个独立数字：本次同步数量默认 50、范围 1–500；自动处理数量默认 20，且不超过本次同步数量与批处理上限 50。同步按钮把用户选择的正整数传给下载器，产品入口不再暴露 `count=0` 无限同步。适配器与前端仍以 `limit=0` 读取本地 manifest 的全部已有条目，避免“限制本次新增”错误变成“隐藏历史视频”。

下载器 manifest 的追加顺序既不等同于作品发布时间，也不等同于收藏顺序：媒体并发下载会打乱 `recorded_at`，重复同步还会让写入顺序更加混杂。下载器 Web 层在调用抖音收藏分页接口时记录返回的 `aweme_id` 顺序，并把本次有限快照与旧快照合并到 `source_order.json`；已下载而跳过的作品也能更新排名。`/api/v1/items` 只返回排名，不伪造不存在的逐条收藏时间。

知萃“收藏”来源默认按 `source_rank` 从小到大显示，即最后收藏的作品在前；用户可切换为按 `publish_timestamp`、日期、采集时间从新到旧。首次升级而尚无顺序快照时，知萃请求下载器仅刷新有限的收藏顺序元数据，不下载媒体；若登录失效或接口受限，则安全回退到发布时间。喜欢和我的作品继续使用发布时间，避免错误套用“收藏时间”语义。

下载器继续独占视频文件和 manifest。知萃同步列表时不写数据库；用户主动生成知识结果后，`Note` 只保存字符串形式的作品标识/来源地址、完整文案、AI 卡片与来源元数据。数据库模型不包含 BLOB、BYTEA 或二进制媒体字段。

## Risks / Trade-offs

- [下载器服务未启动或只绑定本机] → 连接状态接口返回可操作错误，单条提取和已保存知识库不受影响。
- [媒体文件较大导致请求耗时和磁盘压力] → 顺序导入、流式下载、临时目录清理，并限制单次选择数量。
- [下载器媒体 URL 只能在本机访问] → 连接地址由环境变量配置，生产环境必须部署伴随服务或保持连接器关闭。
- [多视频上下文超过模型窗口] → 扫描最多 50 条完整文案，通过规划和全局检索选择上下文；深度模式分批 map-reduce，并返回覆盖统计。
- [深度研究增加 LLM 成本和延迟] → 默认快速模式；深度模式由用户显式选择，并在界面说明会进行多阶段分析。
- [页面关闭导致自动提取中断] → 下载器采集 job 在伴随服务继续运行；知萃单条提取幂等，重新打开后只需继续未完成项。生产级持久队列仍作为后续能力。
- [同一视频重复提取消耗 ASR] → 导入前按 `user_id + video_id` 查找已有 Note，已存在时直接返回该 Note。
- [下载器清单包含图集或缺少视频文件] → DTO 标注是否可提取，前端禁用不支持的条目并保留其说明文字。
- [用户选择较大同步数量并占用本地磁盘] → 默认 50、最大 500，视频只写入下载器目录，AI 自动处理仍限制为最多 50 条。
- [抖音返回删除、私密或风控不可见作品] → 同步结果以当前 Cookie、接口可见性与用户选择的数量为准。
- [收藏接口不返回逐条收藏时间戳] → 持久化接口返回顺序而不伪造时间；已排名作品优先，未覆盖的历史作品使用发布时间稳定回退。

## Migration Plan

1. 部署后端连接器、直接媒体 ASR 和集合问答 API。
2. 部署前端 `/library` 页面和导航入口。
3. 本地默认连接 `http://127.0.0.1:9000`；生产未设置伴随服务时页面显示未连接状态。
4. 本变更不修改数据库结构，回滚只需回退代码；已生成的 Note 仍然是普通兼容笔记。
