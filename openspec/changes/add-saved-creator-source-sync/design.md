## Context

知萃已有三条不完全相同的资料通路：抖音通过用户作用域的服务器 sidecar 同步并按需转写；B站和小红书可逐条导入，桌面端还可借助本地浏览器读取当前账号。指定博主必须在服务器持久运行，供 Web、Android 和桌面共同使用，同时不得把平台凭证、媒体地址或下载文件持久化到业务数据库。

## Goals / Non-Goals

**Goals:**

- 保存最多 50 个用户级博主来源，并按一次一个博主、最近 20/50/100 条手动增量同步。
- 三平台统一 API、持久任务状态、重启恢复、幂等和永久移除保护。
- 同步后准备普通文稿，不执行摘要、视觉解析、Agent 调用或自动化。
- 复用现有连接器和 Note/资料库，不引入不兼容的商业许可证。

**Non-Goals:**

- 定时监控、多博主批量更新、媒体归档、NAS 下载和历史资料自动回填。
- 小红书图文、私密作品、不可见作品或无限滚动全量抓取。

## Decisions

1. **独立持久来源与任务表。** `creator_sources` 保存标准化主页和展示信息，`creator_source_items` 保存用户级平台作品去重与永久移除墓碑，`creator_sync_runs` 保存任务阶段、心跳、计数和最多 100 项的脱敏结果 JSON。相比把来源塞入 Note JSON，这能在 Note 删除后保留防重语义；相比单独 run-item 表，100 项上限下 JSON 更简单且不会保存敏感上游响应。
2. **统一适配器协议，平台实现隔离。** 适配器只返回 `CreatorProfile` 与 `CreatorWork` 安全字段。B站调用 yt-dlp flat playlist；抖音调用带 `X-Zhicui-Scope` 的现有 MIT sidecar；小红书调用 loopback GPL sidecar并由后端注入管理员加密 Cookie。MediaCrawler 不进入依赖。
3. **后台 Worker 使用数据库租约。** 复用项目现有 ThreadPoolExecutor/恢复循环模式，按用户限制一个活动任务，平台信号量限制抖音/小红书各 1、B站 2。活动任务唯一检查与创建在事务中完成，重复请求返回已有任务。
4. **文稿处理复用已有资料服务。** B站与小红书扩展 `platform_library_service` 的单条导入；抖音先让 sidecar 元数据进入用户 manifest，再调用现有 library extraction。所有路径都只创建/刷新普通 Note，显式禁止 AI 初始化与视频详细解析。
5. **删除保留墓碑。** 删除博主只停用来源并保留已导入 Note；永久移除作品时将对应 `creator_source_items.removed_at` 写入，后续发现相同作品计为 `skipped_removed`。运行中来源返回冲突，必须先取消任务。
6. **同一 Sheet 渐进展开。** 平台选择后显示“我的账号 / 指定博主”，指定博主模式内完成解析、保存、选择和启动，不创建新路由。活动任务通过现有全局任务入口恢复。
7. **功能按平台健康门控。** 总开关默认关闭；B站检查 yt-dlp，抖音检查 sidecar 与用户会话，小红书检查 sidecar 与管理员凭证。不可用平台保留说明但禁止启动。

## Risks / Trade-offs

- [平台风控或页面变化] → 适配器隔离、固定上游版本、短超时、健康检查和单平台熔断，失败不影响其他平台资料。
- [共享小红书凭证影响全部用户] → Fernet 加密、仅 loopback 传递、日志脱敏、并发 1，并允许管理员单独停用小红书。
- [进程重启留下运行中任务] → 心跳与租约超时后恢复为 queued；逐作品幂等使重放安全。
- [第三方许可证] → yt-dlp 使用 Unlicense，抖音 sidecar 固定 MIT 上游，小红书 GPL 代码保持独立进程并随部署提供许可证与对应源码信息。
- [100 条连续 ASR 时间较长] → 逐条提交、实时计数、可离页后台运行；失败项不阻塞其余项目。

## Migration Plan

1. 通过 SQLAlchemy `create_all` 创建三张新表并部署默认关闭的 API/Worker。
2. 部署固定版本 sidecar 扩展，完成管理员健康测试与小红书凭证配置。
3. 开启总开关并逐平台开放入口；旧 Note 和同步任务不迁移、不自动执行。
4. 回滚时关闭功能开关并停止 Worker；新表保留只读历史，不影响现有资料库。
