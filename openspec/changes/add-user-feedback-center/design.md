## Context

知萃目前已有 JWT 用户体系、管理端、管理员审计日志和用户活动日志，但没有用户反馈数据模型或产品内入口。网页端和 Capacitor Android 共用同一套 Next.js 客户端，因此反馈入口应放在全局布局中，并通过相同的 FastAPI 接口提交。

反馈内容可能包含用户描述、页面路径和设备环境。实现必须保持用户隔离，不采集认证令牌、密码、视频文件或页面正文，并让管理员处理行为可审计。

## Goals / Non-Goals

**Goals:**

- 为已登录用户提供桌面端和移动端都可达的全局反馈入口。
- 支持分类、主题、详细描述、当前页面和有限设备环境信息。
- 让用户查看自己的最近反馈、状态和管理员回复。
- 让管理员筛选、查看并处理所有反馈。
- 复用现有认证、响应信封、活动日志和管理员审计机制。
- 在固定底部导航和手机安全区存在时保持入口、对话框和提交按钮可用。

**Non-Goals:**

- 本轮不支持图片、视频或其他附件上传。
- 不接入外部工单、邮件或即时通讯系统。
- 不实现实时聊天或推送通知。
- 不允许普通用户查看其他用户反馈。

## Decisions

### 1. 使用独立 Feedback 表而不是复用错误日志

反馈具备用户可见状态、分类、主题和管理员回复，与技术错误日志的生命周期不同。新增独立表，字段包括用户、分类、主题、内容、页面路径、客户端环境、状态、管理员回复和处理人。

替代方案是写入应用错误日志，但会混淆主动建议和系统异常，也无法安全地向用户展示处理状态。

### 2. 用户接口和管理端接口分离

- `POST /api/feedback`：提交反馈。
- `GET /api/feedback`：仅返回当前用户反馈。
- `GET /api/admin/feedback`：管理员分页、筛选和搜索。
- `PATCH /api/admin/feedback/{id}`：更新状态与回复。

所有用户接口使用 `get_current_user`，管理端使用 `get_current_admin`。管理员修改写入审计日志，用户提交写入活动日志。

### 3. 只采集最小客户端环境

客户端可提交当前 pathname、运行平台、浏览器 user agent、视口尺寸和应用版本。服务端限制长度并只保存 JSON；不接收 localStorage、Cookie、请求头、页面正文或媒体文件。

### 4. 使用原生 dialog 作为交互基础

全局 `FeedbackButton` 使用浏览器原生 `<dialog>` 的 `showModal()` / `close()`，复用浏览器焦点管理、Escape 关闭和模态语义，避免手写键盘陷阱。桌面端显示“反馈”文字，窄屏保留清晰图标和无障碍标签。

### 5. 浮动入口遵守现有安全区和导航层级

桌面端入口位于右下角；移动端提升到底部 Tab Bar 之上，并使用 `env(safe-area-inset-bottom/right)`。不增加循环动画或发光效果，只使用不超过 160ms 的局部透明度/位移反馈。

### 6. 数据库级频率限制

每位用户 10 分钟最多提交 5 条反馈，服务端按记录时间查询并返回 429，避免按钮重复点击或脚本刷入。前端提交期间禁用按钮，但不把前端状态作为唯一防护。

## Risks / Trade-offs

- [原生 dialog 在旧 WebView 上行为不一致] → 当前 Capacitor Android WebView 基于现代 Chromium；同时保留普通表单结构和显式关闭按钮。
- [反馈内容含敏感信息] → 表单提示用户不要填写密码/密钥，服务端限制字段并不采集存储数据或认证信息。
- [浮动按钮遮挡业务操作] → 移动端放置在底部导航上方，桌面端使用固定安全间距，并在模态打开时不重复显示入口。
- [管理员回复后用户无法及时获知] → 本轮在“我的反馈”中展示回复与状态；实时通知留作后续能力。
- [SQLite 与 PostgreSQL 时间比较差异] → 使用 SQLAlchemy datetime 字段和 UTC 时间，避免方言专用 SQL。

## Migration Plan

1. 部署包含 Feedback 模型的后端，现有启动 `create_all` 自动创建新表。
2. 部署前端入口和管理端页面；旧客户端不受新增 API 影响。
3. 构建生产 API 地址的 Capacitor APK并替换下载文件。
4. 验证用户提交、用户隔离、管理员筛选/处理、审计日志和移动端安全区。
5. 回滚时可回滚代码；保留 feedback 表和数据，不执行破坏性删除。
