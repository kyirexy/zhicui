## Context

当前 `/library` 内的 `LibraryChat` 已具备完整文案检索、快/深研究、联网校验、证据引用和输出形式选择，但对话只保存在组件内，资料范围来自当前页面或临时勾选项。知萃数据库已经按用户保存文案与视频元数据，服务器不保存视频文件。桌面端有独立侧栏，网页和 Capacitor Android 共用 Next.js 客户端。

每日摘要必须在浏览器和桌面应用关闭后仍可运行，因此调度属于云端后端职责。生产环境当前由单个 FastAPI 服务进程运行，但实现仍需防止未来多进程或重启造成重复发送。

## Goals / Non-Goals

**Goals:**

- 提供独立、持久、以视频资料为上下文的 Agent 工作台。
- 让用户显式选择资料范围，并在回答后持续看到实际资料快照与依据。
- 让每日摘要计划可创建、修改、暂停、试跑、查看运行记录，并把结果保存为可继续追问的 Agent 任务。
- 定时执行不依赖客户端在线；邮件配置缺失或发送失败时保留生成结果与真实状态。
- 保持用户数据隔离，并继续只保存文案、元数据和生成结果。

**Non-Goals:**

- 本次不实现 Gmail/Outlook OAuth 收件箱读取，也不代表用户发送邮件。
- 本次不承诺获得抖音的精确“收藏发生时间”；“昨天”指昨天新整理进知萃且文案就绪的记录。
- 本次不重写已有检索/LLM Agent 链，不把视频文件写入知萃数据库或对象存储。
- 本次不实现任意 Cron 表达式；首版为每天一次的本地时区时间。

## Decisions

### 1. 独立 `/agent` 工作台，视频库只负责采集与管理

Agent 使用一级页面承载任务历史、对话、资料抽屉和自动化入口。桌面端默认只保留可收起的任务栏与主对话两栏，资料范围始终以明确按钮显示，但完整选择器按需从右侧抽屉打开；网页窄屏和移动端把任务历史与资料选择降级为抽屉/底部面板，输入区固定在安全区上方。

替代方案是在 `/library` 继续扩大右侧聊天栏，但它会让同步管理和持续对话争夺空间，且无法形成稳定的任务历史。

### 2. 会话保存“资料快照”，不在每次提问时重新解释“全部”

`AgentThread` 保存 `scope_type`、人类可读范围标签以及去重后的 `note_ids` JSON 快照；消息通过 `AgentMessage` 独立存储。创建会话时，后端只解析当前用户、文案已就绪的 Note，并最多选取 100 条；收藏/喜欢/作品优先使用独立来源台账的同步顺序，而不是误用 Note 创建时间。研究链会在服务端分块扫描全部快照，只把全局相关且来源多样的片段放入有界模型上下文。响应明确区分已扫描来源与实际进入合成上下文的来源，并返回 `available_count`、`selected_count` 和是否截断。

修改资料范围会创建新任务，避免旧回答的证据集合悄然改变。手动选择的 ID 由后端再次校验用户归属。

### 3. 来源选择只依赖知萃数据库，不依赖下载器在线

新增 DB-backed sources API 和独立 `video_source_ledgers` 台账，以用户、视频和来源模式为唯一成员关系，记录 `source_rank`、`first_seen_at`、`last_seen_at` 和 `source_synced_at`。同步使用数据库原生 upsert；资料库 GET 只读台账，不再与 AI 初始化并发改写整段 `Note.ai_summary`。旧记录继续只读 `source_meta` 作为兼容回退。

“昨天新整理”按用户时区筛选该来源模式首次进入知萃的时间；同一个视频新增到另一种来源时拥有独立的首次发现时间。UI 和邮件都使用这一真实表述。

### 4. 复用现有视频问答 Agent 链并持久化完整结果

发送消息时读取会话快照对应的用户 Note，调用 `answer_library_question`，并保存回答、证据、来源上下文、联网来源和追问建议。历史只把最近六轮文本传入现有接口，完整历史仍保存在数据库。

首版沿用非流式接口，页面通过阶段状态提供清晰反馈；用户可停止等待，但同步 LLM 调用仍会在后端完成，页面会轮询任务并自动载入结果，不会把“中止浏览器请求”冒充真正取消。后续可以在不改表结构的情况下增加 SSE token/阶段流与服务端取消协议。

模型输出首先经过服务端响应契约解析，再分别持久化正文、依据、联网来源、可信状态和追问建议。解析器兼容 Markdown 围栏、双重 JSON 编码及网关附加说明；结构化输出无法完整解析时也不会把内部 JSON 直接保存成可见正文。前端对已有异常历史记录做只读恢复，不要求用户清空数据。

### 5. 每日摘要是持久化自动化，执行结果同时成为 Agent 任务

`AgentAutomation` 保存每天时间、时区、收件邮箱、可编辑指令、启用状态、下次运行时间和租约。`AgentAutomationRun` 保存每次执行的资料数量、生成文本、投递状态、错误及关联会话。

手动“立即生成”默认只预览、不发送；定时运行会按配置尝试发送。摘要使用“昨天新整理”资料创建快照和会话，再调用同一个视频 Agent 链生成，用户可从运行记录打开会话继续追问。

### 6. FastAPI 进程内轮询 + 数据库租约，SMTP 使用标准库

启动事件创建一个 30 秒轮询线程，按空闲 worker 数量领取任务并使用独立数据库会话执行；`lease_token`、`lease_until` 和运行心跳防止多实例重复或把长任务误判为失效。服务错过多个日期时只补最近一次计划，且摘要日期以持久化的 `scheduled_for` 为准。应用关闭时停止轮询。

邮件使用 `smtplib`、证书校验 TLS 和 `EmailMessage`，通过可选 `SMTP_HOST/PORT/USER/PASSWORD/FROM/USE_TLS` 配置。实际投递是显式开关，且账号邮箱必须先通过 24 小时签名链接验证。未配置或未验证时摘要仍成功保存；发送异常标记 `failed`，不丢弃结果。手动运行永远是站内预览。

替代方案是引入 Celery/APScheduler，但当前部署没有消息队列且项目依赖较轻，首版不增加运维面。若用户量增长，可让同一任务表由独立 worker 消费。

### 7. 安全边界

除一次性签名邮箱确认外，所有 Agent、来源和自动化 API 都要求 JWT 并按 `current_user.id` 隔离。API 不接受任意会话用户 ID；同一对话串行执行并有用户级提问/预览额度；邮箱只允许当前账号地址且实际外发前必须验证；消息和指令有长度上限；邮件 HTML 转义；日志不记录 SMTP 密码、验证 token 或完整文稿。

### 8. 开源 Agent 架构采用渐进边界

当前版本只接入 AI Elements 的消息渲染能力，保留既有 FastAPI、视频检索、计划与自动化服务，不为更换聊天外观引入第二套状态源。下一阶段优先用 PydanticAI 把检索、完整文稿读取、联网查证、计划操作包装为强类型工具，并以 AG-UI 作为可选的流式协议边界；完整聊天壳可用 assistant-ui 的 External Store Runtime 映射现有会话。

LangGraph 只在出现跨分钟长任务、显式暂停恢复、人工审批分支或 PostgreSQL checkpoint 需求时引入，避免在当前阶段同时维护两套编排器。定时摘要继续由持久调度器执行，Agent 只能创建经过服务端校验的任务记录。

## Risks / Trade-offs

- [现有旧视频缺少来源模式] → 仍进入“全部已有文案”，只在有可靠元数据时进入收藏/喜欢/作品筛选。
- [“全部”超过 100 条] → 只冻结 100 条并显式提示截断；快照内 100 条均参与服务端检索，只有有界片段进入 LLM 上下文；后续可扩展向量索引和持久 map-reduce。
- [应用进程重启时任务延迟] → `next_run_at` 持久化，启动后补跑到期任务；租约过期后可重新领取。
- [SMTP 提供商限流或拒信] → 摘要生成与投递分离，保留失败原因并允许用户重试。
- [SQLite 开发环境并发能力有限] → 单线程轮询且使用短事务；生产 PostgreSQL 使用相同 SQLAlchemy 模型。
- [桌面连接器离线导致昨天没有新资料] → 生成“没有新整理内容”的可解释运行结果，不声称已自动抓取抖音。

## Migration Plan

1. 先部署新增表、来源元数据兼容读取和 API；`create_all` 自动创建新表，旧数据无需回填。
2. 再部署 `/agent` 页面与导航；旧 `LibraryChat` 保持可用作为回滚路径。
3. 配置 SMTP 后再启用实际邮件投递；未配置环境只提供预览。
4. 若需回滚，停止调度服务并回退前端入口；新增表可保留，不影响旧版本。
