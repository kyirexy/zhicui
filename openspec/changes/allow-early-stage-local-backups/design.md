## Context

生产环境当前能够在服务器本机生成加密 PostgreSQL 备份、校验 SHA-256，并在隔离数据库中完成恢复验证；但没有 COS、S3 或独立 SSH 目标。现有发布门禁把异地回读作为无条件要求，因此即使本地恢复证据有效也无法发布。产品仍处于早期阶段，所有者明确接受单机故障域风险，但不能因此取消备份、恢复、冒烟和回滚保护，也不能把本地副本伪报成异地副本。

## Goals / Non-Goals

**Goals:**

- 允许显式、可审计的早期阶段本机备份模式。
- 默认继续要求异地备份；本机模式必须由两个独立配置共同开启。
- 两种模式都强制执行加密备份、校验和、隔离恢复、发布冒烟及失败回滚。
- readiness、运维接口和部署证据如实暴露当前模式与风险接受状态。
- 后续接入 COS/S3/SSH 时仅切换配置即可恢复严格异地门禁。

**Non-Goals:**

- 不把本机备份描述为高可用或灾难恢复完备。
- 不取消数据库备份、恢复验证、权限检查、健康检查或原子发布。
- 本次不采购或配置 COS/S3，也不改变备份加密格式。

## Decisions

### 采用双重显式开关

后端使用 `BACKUP_OFFSITE_REQUIRED=false` 表示选择本机模式，并要求 `EARLY_STAGE_LOCAL_BACKUP_ACCEPTED=true` 表示产品所有者接受风险。备份任务使用 `ZHICUI_OFFSITE_REQUIRED=false`。发布门禁会校验后端与备份证据的模式一致；任一开关缺失都拒绝上线。

相比单一开关，这能避免环境变量遗漏或模板复制意外降低保护等级。默认值仍为异地模式。

### 本机模式保留完整的本地恢复链路

备份脚本仍生成加密 dump 与 SHA-256，恢复脚本仍在隔离数据库中执行真实恢复。仅跳过远端上传和远端回读。发布脚本继续要求备份新鲜度、恢复成功、文件权限、应用冒烟和回滚条件全部通过。

### 状态必须真实表达

本机模式的 readiness 记录 `backup_mode=local_only`、`offsite_required=false`、`offsite_verified=false` 和 `recovery_material_verified=false`。系统不得为了通过门禁写入虚假的异地成功字段。管理端与发布证据可以据此提示单机故障域风险。

### 异地模式保持向后兼容

当 `BACKUP_OFFSITE_REQUIRED=true` 时，行为与现有严格模式一致：必须完成上传、远端回读、恢复材料校验和时间新鲜度检查。

## Risks / Trade-offs

- [服务器磁盘或整机损坏会同时丢失业务库和本机备份] → 明确展示 `local_only`，保留 14 天轮转，并在用户量增长前切换 COS/S3/SSH。
- [配置漂移导致后台与备份脚本模式不一致] → 发布门禁校验配置和 readiness 证据一致，不一致即失败。
- [误把本机模式长期使用] → 默认始终为异地模式，风险接受开关名称明确且运维状态持续可见。
- [跳过异地步骤掩盖其他恢复问题] → 本机模式仍执行真实隔离恢复，不接受仅“文件存在”的假验证。

## Migration Plan

1. 发布支持双模式的代码和脚本，但保持默认异地要求。
2. 在生产后端设置 `BACKUP_OFFSITE_REQUIRED=false` 与 `EARLY_STAGE_LOCAL_BACKUP_ACCEPTED=true`。
3. 在备份环境设置 `ZHICUI_OFFSITE_REQUIRED=false`，重新安装 systemd 备份资产。
4. 重新执行加密备份和隔离恢复，确认 readiness 为 `local_only` 且异地字段为 false。
5. 执行带登录冒烟的原子部署，并确认前后端健康和版本切换。
6. 后续接入远端目标后，把三个模式开关恢复为严格异地配置并完成一次远端回读。

回滚时恢复上一版运行产物；若要恢复严格门禁，将 `BACKUP_OFFSITE_REQUIRED` 和 `ZHICUI_OFFSITE_REQUIRED` 设回 true，并在远端验证通过前停止新部署。
