## Context

现有 `extract_library_item` 在一个锁内完成媒体读取、ASR、DeepSeek 分类、知识卡和可选计划，然后创建一条 Note。资料库用“是否存在 Note”同时表示“有文案”和“已完成 AI”，因此无法保存只有文案的中间状态。问答服务本身已经能在 `ai_summary=None` 时只依据完整文案回答，真正的限制来自持久化与任务状态耦合。

同步范围允许 1–100 条，但现有批量任务固定最多 50 条。用户要求同步范围内的文案全部自动提取，因此转写操作需要接受 100 条并全部入队；实际云端 ASR 请求仍通过现有运行时并发门限控制。为了同时承载多个用户的 100 条任务，进程级执行器容量与管理端 ASR 上限需要提升到 200。

## Goals / Non-Goals

**Goals:**

- 同步完成后自动并发转写本次范围内所有可处理视频。
- 文案保存后立即可用于单视频、多视频问答和计划 Agent。
- DeepSeek 分类、知识卡与计划初始化只由明确的用户操作触发。
- 两个阶段均幂等，重试不会重复 ASR、重复 Note 或重复知识卡。
- 已有 Note 默认视为 AI 已初始化，不破坏线上数据。
- ASR 默认并发为 200，管理员可在 1–200 间热更新；LLM 并发仍为独立的 1–50。

**Non-Goals:**

- 不让 AI 问答绕过完整文案直接猜测视频内容。
- 不把视频二进制保存到数据库或长期保存到服务器。
- 不把单批上限扩大到 200；单个用户的一次同步仍最多 100 条，200 是跨用户共享执行器的系统容量和 ASR 配置上限。
- 不在本次改变 DeepSeek 模型、ASR 供应商或定价策略。

## Decisions

### 在 Note 上增加持久化 `ai_initialized`

新增布尔字段，默认值为 `true`，启动迁移为已有记录补 `true`。自动转写创建的 Note 写入 `false`；AI 阶段完成后更新为 `true`。相比只依靠 `ai_summary` JSON 推断，显式字段更利于列表筛选、API 状态、管理端审计和未来失败重试。

转写 Note 的 `ai_summary` 只保存来源元数据与 `ai_initialized: false` 标记，不伪造 sections、conclusion 或 card_type 结论。问答上下文解析器遇到该标记时返回空摘要。

### 批量任务携带明确 operation

批量 API 增加 `operation: transcript | ai | full`：

- `transcript`：复用已有文案；缺失时只运行 ASR 并保存转写 Note。
- `ai`：要求文案已存在，只运行分类、知识卡和可选计划。
- `full`：兼容现有单条入口，缺什么补什么。

任务快照返回 operation 与每条的 `ai_initialized`，前端据此显示准确进度。

### 转写批次 100，AI 批次 50

线程池扩大到 200，使两个用户各自提交 100 条转写时都能同时进入执行。`transcript` 单批接受最多 100 条；`ai` 与 `full` 保持最多 50 条。ASR/LLM 阶段信号量继续独立限流，数据库连接只在读取和写入时短暂持有。

### ASR 容量由管理端在 1–200 间热更新

运行时 ASR 默认并发调整为 200，服务端校验、设置持久化和管理端数字输入共享同一上限。配置响应同时返回 `max_asr_concurrency` 与 `max_llm_concurrency`，避免前端硬编码。新创建的任务读取最新设置；单批只有 100 条时有效并发自然不会超过 100，但多个用户的任务可共同使用 200 个执行线程。

### 问答以完整文案为最低初始化条件

只要 Note 有非空 `transcript_raw`，即可加入问答来源。`ai_initialized=false` 时不向问答 Agent 提供 AI 摘要，来源上下文显示 `ai_summary_used=false` 或 `ai_summary_count=0`，但完整文案检索、联网查证与引用校验照常工作。

## Risks / Trade-offs

- [同步 100 条需要较长时间] → 所有任务立即入队并展示逐条状态；ASR 并发可由管理端热更新。
- [自动 ASR 产生云端费用] → 范围仍由用户选择且最多 100 条，不会同步整个无限收藏夹。
- [200 并发可能触发供应商限流] → 管理端可随时下调到 1–200，单条失败保留错误并可重试，不影响已保存文案。
- [转写 Note 在知识卡列表中形成空卡] → 用户知识卡列表默认只展示 `ai_initialized=true` 的 Note；资料库和详情页仍可访问文案。
- [旧客户端不知道 operation] → API 默认 `full` 保持兼容，新客户端显式发送阶段。
- [服务重启丢失内存任务] → 已完成文案逐条立即持久化，刷新后只重试仍缺文案的视频。

## Migration Plan

1. 部署后端模型与启动迁移，已有 Note 的 `ai_initialized` 默认为 true。
2. 部署支持 operation 的批量 API，同时保留默认 full 行为。
3. 部署前端自动转写与按需 AI 入口。
4. 验证一条仅文案 Note 可以问答、AI 初始化后同一 Note 被更新而非重复创建。
5. 在生产数据库把 `extraction_asr_concurrency` 设置为 200，重新构建带更新日志的生产 Android APK。
6. 若需回滚前端，旧 full 操作仍可工作；新增列与转写 Note 可保留。
