## Context

`/library` 是产品第二个主导航，但当前页面、API 和前端类型都以抖音下载器清单为中心。B 站已经在 `video_extractor.py` 中使用 `yt-dlp` 取得基础信息、字幕和临时音频，小红书则由 `xhs_extractor.py` 读取标题与正文；两者通过首页单链接流程直接生成知识卡，无法作为“仅文案已就绪”的资料进入视频资料库。

`XHS-Downloader` 2.8（GPL-3.0、Python 3.12+）提供 `/xhs/detail` API，可在不保存作品文件时返回作品元数据和媒体地址。知萃已有“数据库不保存媒体、AI 初始化与转写分离、用户数据隔离”的约束，且生产服务器使用精简依赖，因此不能把上游源码复制进 FastAPI 进程并隐式引入整套依赖。

## Goals / Non-Goals

**Goals:**

- 让用户只在第二个“视频资料”Tab 粘贴 B 站和小红书链接，并在同一工作区看到导入结果。
- 规范化标题、发布文案、作者、封面、标签、来源 URL、媒体类型和媒体访问地址。
- B 站优先用已有字幕，小红书视频同时保留发布文案并提取说话内容；无字幕时统一走临时音频 ASR。
- 复用 `Note + source_meta` 作为用户隔离的资料记录，重复导入不产生重复记录。
- 保持媒体二进制不进数据库，并让临时文件在成功和失败时都被清理。

**Non-Goals:**

- 不实现 OCR、弹幕采集、评论采集、账号主页批量爬取或绕过平台风控。
- 不把 GPL 上游源码复制到知萃后端，也不要求 Web 进程安装上游全部依赖。
- 不在本次变更中长期托管视频文件、增加媒体数据库表或重做抖音扫码同步。

## Decisions

### 1. 使用独立、固定版本的 XHS-Downloader sidecar

将上游仓库作为 `integrations/XHS-Downloader` 子模块固定到已审计提交，保留其许可证与原始历史。知萃通过 `XHS_DOWNLOADER_API_BASE` 调用 `/xhs/detail`，请求 `download: false`，仅消费 JSON 元数据和媒体 URL；sidecar 不可用时回退到现有 `xhs_extractor.py`，并明确提示降级后可能只有发布正文。

选择 HTTP 边界而不是直接 `import` 上游模块，是为了隔离 GPL 源码、依赖版本、运行时配置和故障。选择固定提交而不是跟踪 `master`，是为了避免响应字段或风控逻辑无提示变化。

### 2. 新增统一的跨平台资料导入服务，不复用“立即生成知识卡”的 `/api/extract`

新增服务负责 URL 识别、元数据规范化、文本提取、去重和 `create_transcript_note()` 持久化；API 接受 1–10 条 B 站/小红书 URL，并返回逐条结果。导入只完成资料准备，`ai_initialized=false`，继续符合视频资料库“可先问答、再显式生成知识卡”的产品语义。

直接复用 `/api/extract` 会立即触发 LLM、可能生成计划，并把资料混入“我的知识”，与资料库现有的两阶段模型冲突，因此不采用。

### 3. 以 Note 的 `source_meta` 作为跨平台资料清单

新记录使用 `source_kind=platform-import`，并保存 `platform`、`source_url`、`cover_url`、`author_name`、`caption`、`tags`、`media_type`、`media_url`、`transcript_source` 和导入时间。新增用户隔离列表查询，不增加数据库列或迁移；同一用户按 `platform + video_id` 复用最新资料。

抖音下载器清单仍由原接口提供，前端将两种来源合并成统一展示模型。这样能最小化对正在演进的抖音同步、隐藏和排序逻辑的影响。

### 4. 平台提取策略按“已有文本优先，ASR 补齐”执行

- B 站：`yt-dlp --dump-single-json` 读取简介、作者、封面、标签、字幕清单和网页 URL；人工字幕优先于自动字幕。没有有效字幕时只下载临时音频并调用现有云端/本地 ASR。
- 小红书：sidecar 返回的标题、描述、标签和媒体地址作为发布元数据。图文笔记以发布正文作为资料文本；视频笔记将“发布正文”和“语音转写”以明确分段合并。没有可用媒体地址时仍保存正文，但把 `transcript_source` 标记为 `caption-only`。

媒体 URL 可能过期，因此它是可刷新访问提示而不是永久文件承诺；来源页面 URL 始终保留。

### 5. 在 `/library` 内增加平台导入区和来源筛选

导入区位于视频资料页首部，提供 B 站/小红书平台提示、多行输入、导入进度和逐条错误。跨平台导入卡片与抖音卡片共享视觉密度，但显示平台徽标、作者、文本字数和导入状态。来源筛选允许“全部 / 抖音 / B站 / 小红书”，不改变主导航顺序。

## Risks / Trade-offs

- [小红书 Cookie、令牌或风控导致 sidecar 失败] → 支持环境 Cookie、保留现有抓取器降级、逐条返回可操作错误，不把 Cookie 写入响应或日志。
- [第三方 GPL 依赖影响知萃代码边界] → 固定为独立子模块和进程，通过 HTTP 调用，保留许可证及提交信息，不复制或修改上游代码。
- [媒体地址过期或需请求头] → 将来源 URL 作为稳定入口，保存必要的安全请求头提示，播放/转写失败时重新解析，不承诺长期直链。
- [长视频同步请求耗时] → 单次限制 10 条、逐条返回状态；本次先提供有界导入，后续可沿用批任务框架异步化。
- [现有工作区有大量未提交改动] → 只触碰跨平台服务、API、相关类型和 `/library` 组合点，不格式化或重写无关模块。

## Migration Plan

1. 固定 XHS-Downloader 子模块提交并补充集成、许可证和 sidecar 启动说明。
2. 部署 sidecar（默认 `127.0.0.1:5556`）并设置 `XHS_DOWNLOADER_API_BASE`；未部署时后端仍可使用现有降级抓取。
3. 部署后端新 API，再部署前端导入 UI；无数据库迁移。
4. 健康检查 B 站公开链接、小红书视频链接和图文链接，确认临时文件清理与用户隔离。
5. 回滚时先回滚前端入口和后端路由，再停止 sidecar；现有 `platform-import` Note 仍是合法用户数据，不需删除。

## Open Questions

- 小红书高画质视频仍取决于用户提供的有效 Cookie；首版明确展示能力状态，后续再评估面向普通用户的安全 Cookie 绑定流程。
- 大批量主页/收藏导入不在首版范围，待单链接稳定性和风控表现验证后再设计异步队列。
