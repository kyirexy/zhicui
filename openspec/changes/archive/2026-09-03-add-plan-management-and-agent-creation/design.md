## Context

计划删除的后端能力和确认对话框已经存在，但默认视图缺少管理入口，列表入口又只有图标。另一方面，产品动作注册表已有 `plan.create`，Agent 问答链却仅注册视频研究工具；结构化计划生成器也只在视频抽取或既有计划调整流程中使用，导致这些能力没有形成用户可用的闭环。

## Goals / Non-Goals

**Goals:**
- 让桌面端与移动端用户从计划首页直接找到管理和删除操作。
- 只对明确的自然语言创建请求生成并保存计划。
- 复用现有 `generate_plan`、`plan_to_storage` 和 `plan_service.create_plan`，保持计划数据结构一致。
- 在 Agent 回答结果中携带结构化 `created_plan`，让客户端可直接进入计划详情。

**Non-Goals:**
- 不允许含糊的建议咨询自动产生数据。
- 不替换既有计划调整审批流程。
- 不增加自主后台任务、定时执行或任意外部 Tool。

## Decisions

1. **采用高置信度本地意图门控，再调用现有 LLM 计划生成器。** 创建属于写操作，只有同时包含创建动作和计划对象的肯定表达才进入创建链；“怎么制定计划”“评价这个计划”“不要创建”等咨询或否定表达继续普通问答。相比每条消息先调用一次分类模型，这能减少延迟和费用，同时避免模型分类抖动导致误写。
2. **把计划创建编排放在 Agent 服务边界。** Agent 服务拥有当前用户、冻结资料和 Turn 生命周期，可在同一事务语义下保存用户消息、计划和助手结果；底层继续使用计划服务，不复制 ORM 写入逻辑。
3. **创建结果使用既有 Agent 消息结构扩展。** 回答的 `result` 增加 `type: plan_created` 与 `created_plan` 摘要。旧客户端仍能显示文本，新客户端可渲染进入计划的按钮。
4. **管理入口跳转到现有目标视图。** 不引入新的管理模式或批量删除状态。首页“管理计划”只负责切换至目标列表；每行展示带文字的删除按钮，继续复用既有确认对话框与删除 API。

## Risks / Trade-offs

- [自然语言表达超出本地门控词表] → 覆盖常见“创建/制定/生成/安排/做一个”表达并增加单元测试；未命中时仍可普通回答，不会误写。
- [LLM 计划生成失败] → 不创建空计划，清理孤立用户消息并返回可重试错误。
- [创建请求引用大量视频] → 只提供有界资料上下文，优先保留用户指令，避免超出模型输入。
- [列表删除按钮增加视觉重量] → 使用低强调危险色文字按钮，仅在目标列表出现，确认后才执行。

## Migration Plan

无需数据库迁移。先部署后端意图与创建编排，再部署前端入口；旧客户端与旧 Agent 消息兼容。回滚时移除意图分支和前端显式入口即可，现有计划数据保持有效。
