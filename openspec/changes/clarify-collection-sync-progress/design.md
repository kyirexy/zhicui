## Context

下载器创建收藏任务时只立即返回任务标识和运行状态，总数要等抖音接口返回第一页后才可确定。前端把缺失的 `total` 当成 0，并在运行态拼成“已保存 0 条”。生产日志证明同一任务随后能正常完成 50/50 条，因此问题是发现阶段的状态表达，而不是收藏接口或 Cookie 失效。

## Goals / Non-Goals

**Goals:**

- 把“尚未知道总数”和“任务结束后确实为 0”区分开。
- 运行中只展示已经确认的数据，不用临时 0 制造失败感。
- 最终空结果给出可执行的账号检查建议。
- 收藏说明只描述用户行为和结果。

**Non-Goals:**

- 不修改下载器收藏接口、任务结构或抖音登录方式。
- 不改变 1–100 条同步范围、自动文案提取或 AI 初始化策略。
- 不把本地开发账号与正式账号的抖音会话合并。

## Decisions

### 用纯函数生成收藏任务提示

新增前端状态格式化函数，根据 `status`、`total`、`success`、来源名称和请求数量返回提示：

- 运行且 `total` 未知或为 0：正在读取收藏，不展示数字。
- 运行且 `total > 0`：展示真实的 `success/total`。
- 成功且 `success > 0`：展示真实成功数量。
- 成功且 `success = 0`：提示检查绑定账号或重新绑定。
- 失败：优先显示任务错误。

纯函数便于使用轻量脚本直接验证，不需要引入测试框架。

### 空结果以最终任务状态为准

任务运行中 `total=0` 只是“尚未发现”，不能当作空收藏；只有任务进入成功终态且仍为 0 时，才显示空结果建议。随后仍会重新加载资料库，保证成功同步的条目进入页面。

### 用户说明不暴露技术实现

将 ASR、DeepSeek 等供应商或实现名替换为“整理成文案”“生成知识卡”，保留同步上限、直接提问和不保存视频三个用户真正关心的信息。

## Risks / Trade-offs

- [下载器长时间停留在发现阶段] → 继续保留现有轮询超时和失败提示，不伪造进度。
- [旧任务对象缺失 total/success 字段] → 格式化函数统一按 0 处理，但在运行态显示“正在读取”。
- [真实空收藏与错误登录难以自动区分] → 最终提示同时给出检查账号和重新绑定两个动作，不断言用户没有收藏。
