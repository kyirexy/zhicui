## Context

知萃的移动端由同一套 Next.js 客户端同时服务移动网页与 Capacitor Android。当前功能分布在根布局、全局 CSS、多个页面 CSS Module 和各自的弹层中；桌面 Electron 还复用其中大部分组件。现状已经具备数据能力，但移动端存在技术概念外露、反馈遮挡、设置不可发现、页面头部不统一和计划默认页违约等问题。

## Goals / Non-Goals

**Goals:**

- 让 Android 与窄屏客户端形成完整的普通用户产品，而不是桌面 UI 的压缩版。
- 让系统导航、设置、弹层和所有核心页面使用白色实色与中性灰层级，绿色只承担品牌 Logo。
- 保留视频、研伴、知识和计划的现有数据与交互能力，并在 360–430px 保证可读、可触控、无横向溢出。
- 让计划实现既有“今日 / 目标 / 复盘”契约，移动端完整展示列表与四象限。

**Non-Goals:**

- 不修改后端 API、计费、同步、知识或计划数据模型。
- 不删除桌面端高级模型设置或管理员能力。
- 不引入新的路由框架、组件库或手势依赖。
- 不把生成内容的主题、视频封面或第三方平台品牌强制改成灰度；单色约束只作用于产品界面层。

## Decisions

1. **普通用户信息架构与技术配置分层。** 底部导航继续保留“首页 / 视频 / 研伴 / 知识 / 计划”五个任务入口；设置从 Android 首页的品牌栏进入。小于 768px 时设置导航不展示“AI 服务”，直接访问该 section 也回到“常规”。桌面端继续保留高级配置。

2. **反馈从全局悬浮按钮迁入设置。** 现有 `FeedbackButton` 和原生 `dialog` 保持稳定挂载，只在窄屏隐藏 launcher；设置页通过既有 `zhicui:open-feedback` 事件打开同一弹窗。这样不复制状态，也不引入 Portal 或 React DOM ownership 风险。

3. **移动首页使用专用消费级头部。** `WorkspaceActionHome` 增加绿色叶子 Logo、产品名和设置按钮，下面保持问题优先的工作流。普通移动网页的营销首页仍按下载导向工作，Capacitor Android 使用工作台首页。

4. **模型选择保留能力但降低技术心智。** 移动 composer 使用“回答选择 / 正在准备回答”等用户语言，不显示独立 AI 路由入口；目录中的已发布模型名称和供应商图标仍可用于有明确选择需求的用户。桌面文案可以继续更技术化。

5. **计划默认状态以现有主规格为准。** 计划工作区初始化到 `today`，第二个页签显示“目标”。四象限保留单列手机布局，所有新增与删除交互使用居中或底部安全区内的稳定弹层。

6. **响应式判断只使用共享断点。** React 行为使用现有 `useMediaQuery('(max-width: 767px)')`，CSS 继续使用 767px 断点，避免 DOM 与样式对移动/桌面的判断不一致。

7. **视觉系统通过语义变量收口。** 产品 chrome 使用 `#fff`、暖中性灰、近黑文本和细边界；底部激活态与状态徽标不使用紫色或浅绿色。品牌图片保持原始绿色，视频与第三方平台图标保留内容本身颜色。

## Risks / Trade-offs

- **高级用户在手机上无法配置自有模型** → 移动端仍可使用管理员发布的回答选项；需要 BYOK 时可在桌面设置完成，账号级配置继续生效。
- **隐藏反馈 launcher 可能降低发现率** → 首页提供明确设置入口，设置常规页提供“反馈与帮助”行，避免永久遮挡核心操作。
- **计划默认页改变用户习惯** → 变更回到现有主规格，并让“目标”页仍保持一次点击可达。
- **共享组件改动可能影响桌面** → 所有信息架构差异通过共享 767px 断点或移动专用 class 控制，生产构建后同时回归桌面和移动。

## Migration Plan

1. 先落地移动外壳、设置过滤和反馈入口，不改业务请求。
2. 再调整 Android 首页、研伴文案和计划默认视图。
3. 使用 Edge CDP 在 360/390/430 视口检查所有核心路由、弹层与横向溢出。
4. 通过 Next.js 生产构建后执行 Capacitor production export/sync；若出现回归，可按组件回退，不涉及数据迁移。
