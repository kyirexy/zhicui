## Context

当前 V2 Turn 已有单调 `agent_events`、SSE 重放、租约和工具白名单，但执行粒度与呈现粒度不匹配。一次 `video.transcript_map` 内部会串行完成多个模型批次，只有整个工具结束才产生完成事件；V2 Worker 又没有传入 `answer_delta`，因此最终回答只在 `turn.completed` 后一次性出现。前端从提交时就创建空助手消息，并以 `streamingMessageId` 隐藏等待组件，导致数据库已有动作时主视图仍是空白。

OpenAI Codex 将 item started/completed 与 agent message delta 作为不同事件类型，DeepSeek Harness 将每个工具调用投影为可扫描的单行状态并保持同一 keyed 节点更新。本设计复用这种事件语义和 UI 模式，但不复制其通用 Shell/文件工具，也不改变知萃的视频证据边界。

## Goals / Non-Goals

**Goals:**

- 让用户在 Turn 创建后立即看到真实阶段、工具批次、覆盖数和耗时。
- 将多视频 Map 墙钟时间从完全串行降低为有界并发，同时保持确定性结果和限额。
- 让 V2 的可见答案按持久事件增量到达，刷新后可重放且最终消息不重复。
- 减少最终综合输入，避免把已完成 Map 的大量原文再次完整提交。
- 保持取消、租约、计费、来源隔离和 Claim/Evidence 校验语义。

**Non-Goals:**

- 不引入通用命令执行、文件系统工具、子 Agent 或任意网络工具。
- 不展示模型隐藏推理、完整 Prompt、原始文稿或未脱敏工具结果。
- 不保证所有供应商具有相同首 Token 延迟，也不通过伪造文字制造进度。
- 不改变 V1 非灰度用户的回答协议。

## Decisions

### 1. 采用 item lifecycle 与 answer delta 分离的事件词汇

继续复用 `agent_events`，新增/细化 `turn.map.batch.started`、`turn.map.batch.completed`、`turn.map.batch.failed`、`turn.answer.started` 和 `turn.answer.delta`。SSE 将生命周期事件投影为 `progress`，将答案增量投影为 `delta`；所有事件保留 Turn 单调序号，可从零或未来的确认序号重放。

这比只保存“当前阶段”更接近 Codex 的 item lifecycle，也比在前端猜测动作更可靠。事件 payload 只保存批次序号、来源数、耗时、工具名和答案增量，不保存文稿、模型 JSON、密钥或请求参数。

### 2. Map 使用有界并发、主线程归并

`_deep_library_map` 将批次封装为独立纯结果任务，使用最多 4 个线程并发调用模型。每个线程复制当前 request context，以保持用户模型路由和用量归属；SQLAlchemy Session、Turn 事件和进度回调只由协调线程更新，避免跨线程共享 Session。

批次按完成顺序产生状态事件，但最终 findings 按原批次序号排序后归并，使相同输入保持稳定。单批保留超时，阶段预算到达后不再启动新批次，并将未启动/失败数量作为透明降级信息交给综合阶段。相比无限并发，这能限制供应商突发流量和聊天成本。

### 3. 用小块合并缓冲持久化答案增量

V2 Worker 向 `ask_thread` 传入 `answer_delta`。首个安全可见增量立即落为 `turn.answer.started` 与 `turn.answer.delta`；首段和后续字符都按约 16–24 字的有界块合并，避免逐 Token 提交数据库，也避免供应商首个回调较大时整段突现。完成、异常、取消和租约丢失前必须 flush；只有持有租约的 Worker 可以追加增量。

综合模型仍输出结构化 JSON。流式投影器先输出 `answer`，随后只把每个 claim 的 `text` 和 `explanation` 转成临时 Markdown 标题与正文；evidence、note_id 和其余 JSON 不进入临时回答。这样既覆盖模型生成长 claims 的等待阶段，又让完成时的 canonical 校验结果继续拥有最终决定权。

重连时服务端重放 delta，客户端用同一临时助手消息累加；`done` 到达后用服务端持久化的 canonical message 替换临时消息，而不是再次追加全文。保留最终 Claim/Evidence 校验，canonical message 永远是最终事实来源；流式内容明确处于生成状态。

### 4. UI 用稳定挂载的活动投影替代空白消息

前端维护每个当前 Turn 最近的生命周期投影，以 `event_seq` 去重，并把 started/completed 合并到稳定的 activity key。无论正文是否已经开始，用户问题之后默认只展示一行当前动作；最近 3–5 行轨迹仅在用户主动点开时披露，正文开始时重新收拢。临时助手正文与活动摘要属于同一个连续回答单元，正文下方不再挂独立任务卡，也不为折叠状态保留固定高度。刷新恢复沿用同一投影，不增加 Portal 或手工 DOM 操作。

V2 恢复时以 `active_turn` 作为普通研究任务仍在执行的权威信号；`running_analysis` 继续代表独立的视频画面解析。若会话仍为 `running`，但不存在活动 Turn，且最新终态 Turn 的更新时间不早于会话状态，服务端在读取会话时将其安全修复为 `ready` 或 `failed`。客户端不得仅凭孤立的 `running` 字段无限轮询。

交互优先采用 Codex 的单一焦点：运行时状态始终默认收拢、行尾光标只表达仍在输出。展开后的活动行继续采用可扫描模式：状态点、动作标题、摘要、覆盖数/耗时；不照搬通用工具详情卡。桌面和移动端都保留取消入口、`aria-live` 状态和 reduced-motion 行为。

深度研究与跨来源严格校验分开决策。共同观点、反复主题和对比类问题继续映射全部冻结来源并要求独立来源支持；“完整列出/具体包含/分别说明”这类精确枚举仍进入深度模式，但先扫描全部来源，只映射相关性最高的 12 条，并跳过仅为跨视频共识准备的整稿修复。这样保留引用质量，同时避免一次不必要的长模型往返。

### 5. 综合阶段优先消费 Map 结果并限制原文回灌

深度路径把已验证 Map findings 作为主要综合上下文，只补充排名靠前的有限原文块，并设置字符预算。完整冻结来源仍保留在服务端用于 quote 校验，因此压缩 Prompt 不降低最终逐字验证边界。若 Map 部分失败，回答必须显示实际映射覆盖而不是宣称分析全部来源。

### 6. 客户端使用 Codex 式自适应提交队列

SSE 传输层继续按序解析每个持久 `delta`，但可见正文不再直接跟随每个事件更新 React。每个活动流拥有一个有序文字队列：正常压力下约每 40–50ms 排空 2 个字符，使一个持久块持续覆盖到下一个供应商事件；当队列深度或最旧字符年龄越过阈值时，切换到有界批量追赶；极端重放则在一帧内追平。这是对 Codex `StreamController` + `AdaptiveChunkingPolicy` 的浏览器适配。

状态通知保留 DeepSeek Harness 的帧合并语义：同一绘制帧内到达的多个输入只触发一次 React 发布，同时用 generation token 作废旧帧，防止完成、取消或路由卸载后的迟到回调改写 canonical 消息。`done` 仍与 Codex item completion 一样是权威终态，作废未消费队列并原子替换服务端最终消息，不为了播放字符而延迟完成。

持久 SSE 跟随间隔从半秒级降为低延迟短轮询，减少多个持久 chunk 在同一次查询中成批突发。事件仍先提交数据库再对外可见，因此不牺牲恢复性、去重或租约语义。`prefers-reduced-motion` 下不执行小步播放，但仍保留每帧最多一次发布来限制 Markdown 重算。

### 7. 单视频问答区分“研究回答”和“原文读取”

单视频的“核心观点/总结”仍走结构化综合，但 Prompt 明确禁止把单一来源标成 recurring/common/trend，并要求在证据允许时输出 3–5 个 fact/action claims。若首稿的 claims 全部因引用不精确被移除，执行一次有界修复，而不是只留下 100–180 字 overview。

当且仅当当前范围只有一条视频，且用户明确索要“完整文案、完整文稿、全文、全部字幕或完整转录”时，服务端直接返回已经持久化的原始文稿。该路径不经过生成模型，不改写、不摘要，并作为即时 canonical 回答返回，避免长原文被拆成数千个持久事件。客户端只在存在已核验 evidence 时展示引用覆盖率；运行中的中止动作统一称为“停止生成”。

## Risks / Trade-offs

- [并发提高供应商瞬时请求数] → 默认上限 4，并允许服务端常量下调；仍受每 Turn 工具和批次预算约束。
- [线程中的 request context 丢失导致错误模型或用量归属] → 每个任务使用独立 `copy_context()`，并增加路由回归测试。
- [增量内容随后被证据校验修正] → 流式阶段明确标记“生成中”，完成时以 canonical message 原子替换；最终存储和引用始终只使用校验结果。
- [事件过多增加 SQLite 写锁竞争] → 合并答案字符、只在批次边界写事件，并限制活动保留/渲染数量。
- [供应商不遵守超时] → 租约心跳继续工作；阶段预算停止启动新批次，UI 显示当前耗时并允许取消。
- [小步播放落后模型生成] → 以队列深度和最旧等待时间切换追赶档，大量重放直接追平；canonical 完成永不等待播放队列。

## Migration Plan

1. 先部署事件映射和前端向后兼容解析，未知事件继续按 progress 处理。
2. 再启用有界并发和 V2 answer delta；沿用现有灰度开关与用户白名单。
3. 用 37 条真实资料验证首动作、每批进度、首字时间、刷新重放、取消和 canonical 去重。
4. 若供应商错误率或 SQLite 锁等待升高，可把并发常量降为 1 并关闭 answer delta，旧 `turn.progress`/`done` 仍可工作。

## Open Questions

- 生产观测一轮后再决定默认并发是 3 还是 4；实现和测试按上限 4、可配置常量设计。
- 后续是否把活动详情扩展为可展开的完整研究轨迹，不在本次范围内。
