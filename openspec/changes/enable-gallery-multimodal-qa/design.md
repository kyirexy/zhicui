## Context

资料详情目前把问答能力绑定在 `Note` 和文案上，因此图文作品或转写失败的视频只能停留在“补提文案”空状态。抖音图文查看器的全尺寸图片层还会覆盖左右导航的点击区域。系统已经具备用户级 AI 供应商路由、LiteLLM 图片输入和视频抽帧能力，可以在不引入新依赖的前提下补齐视觉问答。

## Goals / Non-Goals

**Goals:**

- 保证图文上一张、下一张与数字缩略按钮均可点击，并保留键盘可访问性。
- 有有效文案时沿用现有 `/api/notes/{id}/ask`；没有文案时自动改用当前资料的视觉证据。
- 图文携带最多 8 张作品图片，视频携带最多 8 张均匀抽样帧，并调用当前用户的有效模型配置。
- 回答返回视觉来源类型和图片数量，使界面能明确说明回答依据。

**Non-Goals:**

- 不把原始图片、视频帧或完整模型请求持久化到数据库。
- 不用图片识别结果伪造“完整文案”，也不在本次改动中自动生成摘要或计划。
- 不改变已有文案问答的联网查证和引用逻辑。

## Decisions

1. **自动路由而非让用户手动选择模式。** 前端以非空文案为首选依据；不存在时调用新的资料视觉问答接口。这样符合“问的时候自动带着图片”的产品预期，也避免用户理解模型输入方式。

2. **新增用户隔离的作品级视觉问答接口。** 接口以 `aweme_id` 定位资料，先按当前用户的抖音绑定读取作品并执行隐藏状态检查，再准备图片。相比创建一个空文案 Note，这能保持数据语义真实并避免污染检索库。

3. **后端把视觉素材转为 data URL。** 图文图片从本机 companion 以账号会话头读取；视频通过同一受控媒体流均匀抽帧。外部模型无法访问本机 URL，因此由后端进行有数量、单图大小和总大小上限的 base64 编码。

4. **复用用户 AI 供应商路由。** 多模态问答使用当前请求用户的供应商、端点和密钥；当供应商是 OmniRoute 时自动切换到 `auto/vision`，自定义供应商继续使用用户选择的模型。供应商拒绝图片输入时，接口返回明确的能力错误，而不是退化成无依据文本回答。

5. **媒体展示层不接收指针事件。** 图片本身没有点击行为，设置为 `pointer-events: none`，同时提高导航按钮层级。这比仅调高按钮层级更能防止透明或 contain 留白区域继续拦截操作。

## Risks / Trade-offs

- [多张原图会增加请求体和模型延迟] → 最多携带 8 张，并限制单图及总字节数；界面在请求中显示正在读取画面。
- [部分自定义模型仅支持文本] → 捕获供应商能力错误并提示用户切换到支持图片的模型，不生成猜测性回答。
- [本机缺少 ffmpeg/ffprobe 时视频无法抽帧] → 图文不受影响；视频返回“暂时无法读取画面”的可恢复错误，保留原有补提文案入口。
- [视觉回答没有逐字文案引用] → `source_context` 明确标记 `visual`、媒体类型和图片数，不展示伪造的原文引用。

## Migration Plan

无需数据库迁移。先部署后端视觉问答接口，再部署前端自动路由；回滚时移除前端调用和新增接口即可，已有 Note 问答不受影响。
