## Context

现有前端调度器只调用一次抖音 `collect` 模式，再为未提取条目启动批量文案任务。抖音接口已经支持 `collect`、`like` 和 `post`；B 站、小红书账号同步则依赖 Electron 本机浏览器 profile，可能打开官方页面并要求用户确认。

## Goals / Non-Goals

**Goals:**

- 自动同步覆盖抖音收藏、喜欢和作品。
- 不重复提取跨来源重复出现的同一作品。
- 短暂文案失败自动重试，永久失败保留真实、安全的原因。
- 区分资料同步失败与文案部分失败。
- 清楚说明 B 站、小红书为什么仍需用户主动同步。

**Non-Goals:**

- 不让后台定时器静默打开 B 站或小红书官方页面。
- 不上传或复制本机第三方平台登录态。
- 不新增服务端调度器、数据库字段或平台抓取接口。

## Decisions

1. **抖音三种来源顺序执行。** 复用现有后端采集任务和轮询接口，避免并发采集争用同一账号会话；某一来源失败时继续处理其余来源。
2. **以作品 ID 去重文案目标。** 每个成功来源刷新自己的列表，将可提取且尚无文案的作品 ID 加入集合，最终受批量接口 100 条上限约束。
3. **失败项只重试一次。** 第一次批次完成后仅提交错误项，避免重复处理成功项；仍失败的条目留到下个周期继续尝试。
4. **增加 `partial` 状态。** 只要至少一个资料来源成功，资料更新就记为成功时间；来源或文案部分失败显示“部分完成”，不再误报整次同步失败。
5. **B 站和小红书保持显式用户操作。** 两个平台的本机账号采集可能需要登录验证或个人主页确认，后台定时器不得静默调用；设置页提供“管理多渠道”入口。

## Risks / Trade-offs

- **[三种抖音来源增加一次执行耗时]** → 顺序执行并保持全局运行锁，设置页显示当前来源进度。
- **[重复重试增加 ASR 请求]** → 只重试失败项一次，后续交给下个用户配置周期。
- **[真实错误过长或包含内部信息]** → 后端已有安全错误截断，前端再次限制为 120 字。
- **[用户误以为 B 站、小红书也会后台自动打开]** → 设置页明确标记为“需要你确认”，只提供资料页入口。

## Migration Plan

前端发布后沿用现有设备级周期和状态存储；旧状态缺少 `partial` 不影响读取。回滚时恢复单一 `collect` 编排即可，不涉及数据迁移。

## Open Questions

无。若未来需要 B 站、小红书无人值守同步，应单独设计平台允许的服务端授权或原生后台方案。
