## Context

系统已有 `user_activity_logs` 表、中间件级非 GET 请求记录、认证成功事件和管理端用户操作表格，但日志只有接口、状态码、耗时和 IP。抖音同步是异步任务：POST 只代表任务已发起，最终数量在后续 GET 轮询中才出现，因此现有日志无法表达一次同步的完整生命周期。生产同时使用 PostgreSQL，开发使用 SQLite，且项目没有 Alembic，需要继续采用可移植的启动时增量迁移。

## Goals / Non-Goals

**Goals:**

- 记录注册、登录以及抖音同步开始、完成、失败的时间和结果。
- 为同步事件保存来源、计划数量、成功、失败、跳过等白名单元数据。
- 让终态轮询日志幂等，同一任务终态只写一次。
- 支持管理端按用户和操作类型筛选，并以中文摘要展示详情。
- 保证旧日志和旧数据库可继续读取。

**Non-Goals:**

- 不记录密码、Cookie、JWT、请求正文、用户问题、视频文案或媒体文件。
- 不把所有 GET 页面浏览都记录为行为日志。
- 不引入第三方埋点平台、消息队列或新的迁移框架。
- 不改变同步任务本身的执行、限额和媒体存储策略。

## Decisions

1. **在现有表增加 `detail_json` 与 `event_key`。**
   `detail_json` 保存小型白名单 JSON，兼容 SQLite/PostgreSQL 且无需引入 JSON 方言差异；`event_key` 使用唯一索引保证异步终态轮询幂等。相比新建多张事件表，这能复用现有报告、分页和保留策略。

2. **详情在服务层执行字段白名单和长度限制。**
   调用方只能写入同步来源、数量、结果等预定义键；未知键被丢弃，字符串和集合均有上限。相比依赖每个路由自行脱敏，集中式白名单更不容易泄漏凭据。

3. **认证采用显式业务事件，通用中间件继续排除认证路由。**
   注册和登录需要知道业务成功/失败，而 HTTP 200 信封并不能表达业务失败，因此在路由中显式写入 `outcome` 和审计状态。失败登录仅在能解析到既有用户时关联用户 ID，否则记为匿名尝试，不保存输入的账号文本。

4. **同步开始在 POST 路由显式记录，终态在 job 查询路由记录。**
   POST 事件写入请求数量、来源和任务 ID；轮询读到 `success`/`failed` 时写入最终统计，并通过 `event_key` 去重。通用中间件不再为同步 POST 额外生成重复的无详情事件。

5. **管理端继续使用一个报告接口。**
   `/api/admin/user-activity` 增加可选 `user_id`，返回解析后的 `detail` 与 `detail_summary`。前端提供用户搜索/选择和操作筛选，不暴露原始 JSON 作为主要界面。

## Risks / Trade-offs

- **[轮询并发导致重复终态写入]** → 数据库唯一 `event_key` 加服务层冲突回读，确保最终只有一条。
- **[日志详情被误用来写敏感字段]** → 服务层严格白名单、类型限制和单条大小限制，未知字段直接丢弃。
- **[已有数据库缺少新列]** → `_migrate_db()` 仅做可空列和唯一索引的增量迁移；旧行自然返回空详情。
- **[登录失败无法关联用户]** → 仅在账号确实存在时关联其 ID，未知账号不落原始标识，隐私优先于完整归因。
- **[同步任务未被再次轮询到终态]** → 本轮仍依赖现有前端轮询；管理端至少可看到“已开始”。持久化任务回调不在本次范围。

## Migration Plan

1. 部署包含模型与 `_migrate_db()` 的后端，启动时增加可空列和唯一索引。
2. 新代码开始写入结构化事件，旧日志继续按空详情展示。
3. 部署前端后启用用户筛选和摘要列。
4. 如需回滚，旧代码会忽略新增列；无需删除数据或索引。

## Open Questions

无。当前需求所需字段可由现有认证和同步任务响应提供。
