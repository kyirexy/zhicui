## Context

视频库同步分成两个客户端阶段：先等待抖音元数据采集任务完成，再加载资料库并为缺失文案的视频创建 `transcript` 批任务。批任务已经支持并发、逐条状态和纯文本持久化，但客户端在采集任务报告 `total=0` 且 `success=0` 时会直接返回，因此不会检查已有资料库中尚未提取的文案。

## Goals / Non-Goals

**Goals:**

- 每次成功完成同步请求后，都以当前资料库和用户选择的同步范围为准检查缺失文案。
- 继续复用现有并发文案批任务和逐条完成更新。
- 文案完成后即可问答，不隐式启动 LLM 总结、知识卡或计划生成。
- 保持文本与元数据持久化，服务器不保存视频文件。

**Non-Goals:**

- 不改变抖音采集器、排序或同步上限。
- 不创建新的后台队列、API 或数据库字段。
- 不自动重试已明确失败的文案任务，也不自动生成 AI 卡片。

## Decisions

1. **移除客户端的“0 条采集结果直接返回”。** 采集结果只说明本次下载器是否新增或更新元数据，不能代表资料库范围内没有缺失文案。同步成功后始终调用 `loadItems(true)`，再从前 `requestedCount` 条中筛选可处理且未提取的项目。

2. **继续使用 `operation: transcript`。** 现有批任务已经为每个项目提交并发工作、以 800ms 轮询并逐条更新 `extracted_note_id` 和 `transcript_chars`，无需新增逐条请求或 LLM 调用。

3. **保留“没有目标”的友好完成提示。** 如果刷新后的范围确实没有缺失文案，才显示“完整文案均已就绪”；永久隐藏的说明仍按现有分支展示。

4. **不把同步数量解释为新增数量。** 自动文案目标取当前来源排序中的前 N 条，而不是只取本次新同步的条目，保证重复点击同步也能补齐缺失文案。

## Risks / Trade-offs

- **[同步返回 0 可能源于上游异常]** → 仍只处理本地已有且 `can_extract` 的项目，不虚构新视频，也不扩大用户选择范围。
- **[重复同步会再次检查已有文案]** → 筛选 `!item.extracted`，后端还通过用户/视频锁和幂等 Note 查询避免重复 ASR 与重复记录。
- **[大范围处理耗时]** → 继续使用管理员配置的并发上限和现有逐条可见进度。

## Migration Plan

仅发布前端逻辑即可，无数据库迁移。回滚时恢复旧前端分支，已有文案 Note 不受影响。
