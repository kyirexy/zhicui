## Context

单视频问答目前把“必须忠于原文”实现成了单一限制：只要原文没有直接给出答案，模型就被要求拒绝回答。这个策略适合事实核对，却会误伤“给一个示例”“帮我写一版”“随便生成一个”等明确的创作请求。连续对话中，用户已经纠正意图后，助手仍会重复来源不足提示。

前端的问答内容、推荐问题、证据和输入表单处于同一滚动流。消息变长后，输入框会离开视口，尤其影响右侧桌面面板和移动端问答 Tab 的连续使用。

## Goals / Non-Goals

### Goals

- 在单视频问答中区分事实核对与创作协助两种任务模式。
- 事实模式继续逐字校验证据，不把推断或生成内容伪装成原文。
- 用户明确请求示例、提示词、改写或头脑风暴时直接给出可用内容。
- 创作回答在接口与界面中明确标记为 AI 生成。
- 最近一轮用户指令和纠正优先于更早的对话意图。
- 让右侧问答区形成固定信息头、独立滚动内容区和常驻底部输入区。

### Non-Goals

- 不引入联网搜索或笔记之外的事实来源。
- 不改变数据库结构，不持久化聊天记录。
- 不放宽服务端证据逐字匹配规则。
- 不改造多视频资料库问答协议。

## Decisions

### 1. 在服务边界做确定性的任务模式识别

服务端根据当前问题中的明确创作信号识别 `creative` 模式，例如“给个示例”“帮我生成”“随便写一个”“改写”“起草”。其他问题默认进入 `grounded` 模式。模式由服务端确定并写入提示词，不完全信任模型自行判断。

原因：同一段原文可能同时支持事实问答与创作延展；把模式写进提示词比继续叠加“来源不足”规则更清晰，也能稳定处理用户纠正。

### 2. 用 `answer_mode` 做增量 API 扩展

`POST /api/notes/{note_id}/ask` 的响应新增 `answer_mode: "grounded" | "creative"`。现有 `grounded` 字段仍只表示是否存在通过逐字校验的证据。创作回答可以带有支撑创作方向的原文证据，但不会因为有证据就被标成“原文答案”。

前端把旧响应中缺失的 `answer_mode` 视为 `grounded`，保证滚动部署和旧本地会话兼容。

### 3. 创作模式仍保留来源边界

创作模式要求助手先直接交付内容，并明确说明这是 AI 生成示例、不是原文原句。数字、人物、产品参数和因果关系仍不得伪造；证据只引用生成所依据的原文方向，生成结果本身永远不进入 evidence。

### 4. 对话区采用三段式 Flex 布局

`ContentChat` 拆分为固定顶部、内部可滚动内容区和底部 composer dock。桌面右侧面板和视频详情问答 Tab 使用受视口约束的高度，滚动仅发生在消息区；移动端保持页面布局兼容，并为底部输入区加入安全区内边距。

## Risks / Trade-offs

- 关键词识别可能把少量模糊请求归入错误模式。通过仅使用强创作信号、默认事实模式来降低误判。
- 创作回答可能比事实回答更长。通过现有字数边界和内容区独立滚动控制布局。
- 移动端软键盘会改变可视高度。使用弹性布局和 `env(safe-area-inset-bottom)`，不依赖固定像素定位。
- 后端先于前端部署时，新字段会被旧客户端忽略；前端先部署时则使用兼容默认值。

## Migration Plan

该变更不需要数据库迁移。后端与前端可独立滚动部署；验证通过后随常规 Jenkins 流程发布。出现异常时可回滚代码提交，现有笔记和会话不受影响。
