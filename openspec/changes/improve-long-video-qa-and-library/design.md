## Context

笔记问答当前会在转录超过 14,000 字符时保留前 9,500 字和后 4,000 字。这个策略能覆盖开场和结论，但完全丢弃视频中段，且回答证据只标注为“视频转录原文”，用户不知道依据大致位于文稿何处。

知识库的用户列表接口只有分页参数，前端列表使用统一的玻璃卡片网格。随着用户笔记增多，标题查找、类型聚合和视觉辨认都会变慢。本变更不引入向量数据库、搜索服务或数据库迁移。

## Goals / Non-Goals

**Goals:**

- 使用当前问题和最近对话，从完整长转录中选择最相关的多个片段。
- 保持发送给模型的上下文有明确上限，并继续严格校验原文证据。
- 为转录证据提供 0-100 的大致文稿位置百分比。
- 让用户可以在自己的全部笔记中按关键词和类型搜索，并获得正确分页总数。
- 让知识库卡片呈现当前视觉主题、内容类型、摘要和清晰的打开动作。

**Non-Goals:**

- 不引入向量嵌入、外部检索服务或额外 LLM 调用。
- 不声称位置百分比是视频播放时间。
- 不提供跨用户或管理员范围的搜索。
- 不修改笔记数据模型或保存每张笔记的独立列表主题。

## Decisions

### 1. 使用确定性的轻量分段检索

长转录按固定长度与少量重叠切分。检索信号由当前问题和最近用户问题中的英文/数字词、中文二元和三元片段组成；对每个文稿片段进行本地词频加权，选取最高分片段并按原始顺序拼接。没有有效检索信号时，均匀抽样覆盖全文。

选择本地词法检索而不是向量检索，是因为它无新依赖、无额外网络延迟、不会把用户全文发送给第二个服务，并能准确命中产品名、人物、数字和中文短语。

### 2. 上下文片段带位置标记，证据仍只接受原文

每个送给模型的片段前加入“原文约 N% 处”标记，用于理解顺序，但模型的 evidence quote 仍必须逐字来自文稿。服务端在完整原文中查找保留证据并计算 `position_percent`，前端展示为“文稿约 N% 处”。

### 3. 搜索和筛选在服务端、用户范围内完成

`GET /api/notes` 接受可选 `q` 和 `card_type`。查询始终先约束 `user_id`，关键词匹配标题和结构化摘要，类型使用受限枚举。总数和分页来自同一过滤查询，避免只筛选当前页的误导结果。

### 4. 知识库列表使用独立轻量预览组件

列表不挂载完整 GSAP 卡片主题，而复用现有 `StylePreview` 绘制低成本缩略图。首张结果在桌面端形成更宽的重点卡片，其余保持自然网格；搜索和分类操作保持在列表上方，并在加载时只替换结果区。

## Risks / Trade-offs

- [词法检索无法理解同义词] → 知识卡片摘要仍始终提供语义概括，并将最近对话加入查询信号；后续有规模需求时再评估向量检索。
- [通用概括问题没有明显关键词] → 使用均匀抽样而不是只取首尾，覆盖整段内容。
- [相同原句多次出现] → 位置取第一次匹配，界面明确显示“大致位置”。
- [对 JSON 摘要执行模糊搜索成本增加] → 查询限定单个用户且现阶段数据规模较小；不新增索引，避免 SQLite/PostgreSQL 方言迁移复杂度。
- [列表缩略图与完整卡片有差异] → 使用同一主题元数据和现有预览组件，明确其用途是视觉辨认而非完整渲染。

## Migration Plan

1. 部署后端兼容扩展：旧客户端不传新参数时查询行为不变。
2. 部署前端搜索、筛选和位置显示。
3. 无数据库迁移和回填；回滚前端或后端均不会破坏已有数据。

## Open Questions

- 当单用户笔记规模达到需要专用全文索引的量级时，再根据 SQLite 与 PostgreSQL 的实际部署分别设计索引方案。
