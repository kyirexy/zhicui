## Context

当前前端在全局 `Providers` 中挂载 `LibraryAutoSyncScheduler`。只要本地设置保存了非零周期，它会在应用启动、回到前台、网络恢复及每分钟检查时调用 `runLibraryAutoSync`，进而读取抖音收藏、喜欢和作品。设置页同时允许重新启用周期。博主任务上下文的轮询只读取已有运行状态，不会创建任务，应继续保留。

第三方平台对账号列表接口存在频率限制和风控。即使同步默认关闭，历史用户的本地非零设置也会在升级后继续生效，因此只隐藏设置入口不足以消除风险。

## Goals / Non-Goals

**Goals:**

- 从运行树中移除所有会创建平台同步任务的定时、启动、可见性和联网恢复调度。
- 将历史自动同步周期迁移为关闭，并让未来写入也只能得到 `0`。
- 保留用户点击同步按钮后的即时同步、任务进度轮询、失败重试和已经启动任务的恢复。
- 在设置页明确解释“仅手动同步”及其风控原因，并提供前往同步页的入口。

**Non-Goals:**

- 不取消用户点击同步后自动准备文稿；该处理不增加平台列表读取频率。
- 不取消已经显式启动任务的后台执行、租约恢复或状态轮询。
- 不改变第三方连接器、同步 API 或数据库结构。

## Decisions

1. **从 `Providers` 中移除调度器挂载，而不是仅让周期默认为零。** 这从组件树层面保证应用启动、恢复可见和网络恢复时都没有同步调用。仅改默认值无法覆盖已有非零本地偏好。
2. **保留设置字段但将其规范化为零。** 这样旧本地数据可平滑迁移，避免破坏 `UserSettings` 的序列化兼容性；后续可在独立清理中删除字段。
3. **把原自动同步设置卡改成只读的“手动同步”说明卡。** 用户仍能找到同步入口，但不能重新启用周期；按钮跳到同步管理界面，实际平台请求仍发生在用户明确点击同步操作后。
4. **保留 `CreatorSyncContext` 和各任务轮询。** 轮询仅查询已存在任务，不触发平台读取；移除它会造成用户手动同步后跨路由丢进度。
5. **保留 `libraryAutoSync.ts` 作为兼容代码但不再从产品运行路径调用。** 这能避免在脏工作树中进行大范围删除，同时用调用点测试保证它不可达。

## Risks / Trade-offs

- [用户误以为任务轮询仍是自动同步] → UI 明确区分“任务状态跟踪”与“创建新同步”，只对后者使用手动触发文案。
- [历史浏览器标签页仍运行旧构建的定时器] → 新版本加载后不再挂载调度器；开发桌面端重启验证。生产部署时旧页面需刷新才能获得新行为。
- [保留的兼容函数未来被误用] → 增加静态测试，断言全局 Provider 不挂载调度器、设置值强制为零且设置页不出现周期选择。

## Migration Plan

1. 更新设置规范化逻辑，使任何历史非零周期读取后保存为零。
2. 从全局 Provider 移除调度器。
3. 将自动同步设置 UI 替换为手动同步说明与入口。
4. 运行目标测试和生产构建，重启桌面端验证不会在启动时产生收藏/喜欢/作品采集请求。

回滚时可恢复 Provider 挂载与周期规范化，但不需要数据库回滚。
