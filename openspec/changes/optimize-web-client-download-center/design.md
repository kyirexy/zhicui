## Context

当前 Web 营销首页已经有 Android APK 与 Windows 安装包链接，但组件内硬编码了版本号，顶部导航会按断点只显示其中一个平台，且下载区仍带有旧的浅绿色文字与图标。Android 和 Windows 均已有同源公开发布清单，因此 Web 可以在不新增后端 API 的情况下展示真实发布信息。

约束包括：Next.js 静态/客户端渲染、公开下载无需登录、任一清单异常不能拖垮首页、不能通过设备识别替用户自动下载，以及需保持 React 19 的稳定 DOM 所有权。

## Goals / Non-Goals

**Goals:**

- 让首次访问者在 Hero、顶部入口和下载中心都能明确发现两个客户端。
- 以公开清单为单一发布信息来源，并对独立失败提供可靠回退。
- 在不隐藏选项的前提下给出本机平台推荐。
- 使用纯白、灰黑和平台图标完成更简洁的视觉层级，绿色只用于品牌 Logo。
- 保持下载链接无需登录并可被键盘和触屏正常使用。

**Non-Goals:**

- 不重新构建或修改 Windows/Android 安装包。
- 不改变原生客户端的自动更新机制。
- 不新增服务端数据库、下载统计或鉴权接口。
- 不实现浏览器指纹、强制跳转或自动开始下载。

## Decisions

### 1. 由首页客户端并行读取两个静态发布清单

首页在挂载后使用 `Promise.allSettled` 并行请求 Android 与 Windows 清单，分别校验必要字段，再单独更新平台数据。这样一个清单不可用时，另一个平台仍可显示真实数据；失败平台继续使用随代码发布的安全回退值。

备选方案是新增聚合后端 API，但这会给纯静态发布信息引入不必要的服务端依赖，并使下载页受登录/后端可用性影响。

### 2. 设备识别只用于“本机推荐”标签

浏览器挂载后根据 user agent 区分 Windows、Android 与其他平台；识别结果只改变推荐标签，不改变链接可见性、不重排主要 DOM，也不自动下载。这避免 hydration 跳变，并允许用户为另一台设备下载安装包。

### 3. 顶部导航使用统一锚点入口

顶部导航不再按桌面/移动断点直链单个平台，统一跳转到 `/#download`。Hero 与下载中心始终并列提供两个平台的直接下载链接，形成“顶部发现—下载中心选择—直接下载”的清晰路径。

### 4. 发布清单提供展示所需元数据

Windows 清单补充 `size_bytes`；首页统一格式化字节数，并显示版本、架构、大小和发布时间中的必要信息。下载 URL 只接受同源相对地址或 HTTPS 地址，字段校验失败时回退到已知可信的官方地址。

### 5. 视觉只使用中性色与平台图标

下载按钮和卡片采用白色、浅灰边界、黑灰文字；Windows 使用显示器/Windows 语义图标，Android 使用手机语义图标。二维码前景改为中性深灰。品牌 Logo 保留原有绿色，但下载区不再用绿色表达状态或主按钮。

## Risks / Trade-offs

- [首次渲染短暂显示回退版本] → 回退版本与当前正式发布保持一致，异步数据只更新文字，不移动主结构。
- [浏览器 UA 识别不完整] → 未识别设备不显示“本机推荐”，两个平台入口仍完整可用。
- [清单内容格式错误或地址不可信] → 逐字段校验并独立回退，不把无效 URL 写入链接或二维码。
- [Windows 文件未随 Next 静态目录提交] → 清单继续使用已验证可访问的生产 HTTPS 安装包地址，本地预览仍可下载正式版本。

## Migration Plan

1. 补充 Windows 清单文件大小并发布 Web 静态资源。
2. 发布首页与顶部导航改造；无需数据库迁移。
3. 在桌面和手机宽度验证两个链接、推荐标签和二维码。
4. 如需回滚，仅回退前端组件与清单字段；现有安装包和原生更新流程不受影响。
