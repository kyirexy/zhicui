## Context

Windows 桌面端加载与网页端相同的 Next.js 客户端，并通过 `window.zhicuiDesktop` 暴露受限的本机能力。当前根布局只有网页顶部导航和营销首页，Electron 运行时没有独立信息架构。移动端刚完成安全区和更新适配，因此桌面重设计必须严格限定在显式桌面运行时，不能依靠视口宽度误伤普通网页。

## Goals / Non-Goals

**Goals:**

- 让 Electron 用户一打开应用就看到可执行的工作台，而不是网站营销页。
- 建立桌面专属的导航、页面标题、账号状态和更新入口。
- 提升 1080px 以上窗口的信息密度，同时保留清晰留白和键盘焦点。
- 让视频库、知识库、计划和设置共享统一桌面视觉语言。
- 保持现有业务组件、路由、API 与用户数据完全兼容。

**Non-Goals:**

- 不为普通浏览器新增第二套网页导航。
- 不重写视频库、问答或计划的业务逻辑。
- 不引入新的组件库、动画库、后端接口或数据库字段。
- 不处理 macOS/Linux 桌面发布。

## Decisions

1. **以 preload 能力作为唯一桌面判定。** 新增客户端 `DesktopAppFrame`，调用 `detectDesktopRuntime()` 后设置 `html[data-desktop-app="true"]` 并渲染桌面导航。仅视口变宽不会启用桌面壳，避免网页端被误判。

2. **采用固定工作导航轨道 + 页面内容标题条。** 左侧轨道承载工作台、视频库、知识库、计划、设置和管理端；顶部标题条显示当前位置、账号、开发/正式运行状态和更新入口。相比继续扩展网页顶栏，这更接近桌面工具的信息架构，并让页面内容获得稳定坐标。

3. **根页面按运行时切换。** 普通 Web 继续渲染现有营销首页；Electron 渲染 `DesktopWorkspaceHome`。工作台复用 `listDouyinLibraryItems`、`listNotes`、`listPlans` 与 `getPlanStats`，请求失败时保持各分区独立可用。

4. **视觉采用冷灰纸面与单一翡翠绿。** 桌面壳使用实色分层、细边界和低对比阴影，不新增渐变或大面积玻璃模糊。工作台不使用等宽指标卡阵列，而以一条概览、一个视频主队列、一个今日计划区和知识行列表建立编辑型层级。数字使用 tabular figures，标题使用平衡换行，正文使用 pretty 换行。

5. **桌面样式通过运行时属性覆盖现有页面。** 在 `globals.css` 中使用 `html[data-desktop-app="true"]` 限定主内容宽度、页面背景、卡片圆角和工具栏间距；业务组件只在需要语义标题时增加稳定 class，不复制整页。桌面壳优先使用 Phosphor light 图标，选中项才提高图标重量。

6. **交互反馈控制在 180ms。** 导航、按钮和卡片只使用颜色、透明度和小范围 transform；尊重 `prefers-reduced-motion`，不增加循环动画。

## Risks / Trade-offs

- **[桌面检测在首帧后完成，可能短暂出现网页顶栏]** → 在 `<head>` 中同步检测 preload 全局并设置运行时属性，React 组件随后校准状态。
- **[工作台并行请求失败导致空白]** → 使用 `Promise.allSettled`/独立响应处理，每个分区都有空态和明确入口。
- **[全局 CSS 覆盖可能影响网页]** → 所有新桌面规则必须以 `html[data-desktop-app="true"]` 开头，并在普通 1440px Web 视口回归。
- **[较窄桌面窗口空间不足]** → Electron 最小宽度维持现有 1080px；在 1180px 以下收窄导航轨道并隐藏次要说明。
- **[远程 UI 更新与旧客户端 bridge 版本差异]** → 桌面壳只依赖已存在的 `getRuntimeInfo`，其他 bridge 能力继续特性检测。

## Migration Plan

1. 先上线兼容普通 Web 的前端代码；没有 preload bridge 的浏览器保持原样。
2. 重新构建 Windows 1.0.2 安装包，让桌面端加载新壳并保留自动更新。
3. 在本地 Electron 开发模式验证所有路由与返回导航。
4. 若需回滚，只移除 `DesktopAppFrame` 和桌面属性样式，业务页面与 API 无需迁移。

## Open Questions

无。当前使用既有路由与数据接口即可完成首版桌面工作台。
