## Context

知萃现有 `/library` 已承担视频同步、导入、检索、预览与文稿处理；`/agent` 以视频 Note 作为唯一资料范围；`/notes` 却再次把全部视频 Note 与用户原创 `KnowledgeEntry` 合并展示。当前混合服务先分别查询两张表，再在 Python 中排序和分页，前端又对当前页执行来源过滤，因此“我的笔记”可能显示错误空状态，计数与分页也不准确。

现有 `KnowledgeEntry` 已具备用户隔离、CRUD 与简单搜索，适合作为知识页的兼容基础。现有 `Note`、视频摘要和历史深链必须保留；本次不重写视频抽取与 Agent 链路，也不删除历史字段。

## Goals / Non-Goals

**Goals:**

- 让 `/library`、`/agent`、`/notes`、`/plans` 分别承担资料、研究、沉淀和行动。
- 让用户原创内容成为可编辑知识页，让具备真实 AI 摘要的视频成为可整理候选。
- 提供从候选到知识页的显式、幂等保存动作并保留来源引用。
- 让搜索、视图筛选、计数和分页都由服务端给出准确结果。
- 提供桌面稳定主从阅读与移动端单列详情，同时兼容旧链接。

**Non-Goals:**

- 本次不让原创知识参与 Agent 检索，也不宣称“向全部知识提问”。
- 不实现向量检索、知识图谱、Claim/Evidence 表、自动判真或版本分支。
- 不迁移、删除或重生成现有 Note，不改变视频文件存储边界。
- 不新增 UI 框架、状态库或动画依赖。

## Decisions

### 1. 将 Note 保持为来源，将 KnowledgeEntry 演进为知识页

扩展现有 `knowledge_entries`，增加 `summary`、`status`、`origin` 与可空 `source_note_id`。旧数据和用户直接创建的数据默认为 `status=canonical`、`origin=manual`；由视频候选保存的页面为 `origin=video` 并关联来源 Note。

选择扩展现有表而不是新建第三张 artifact 表，是为了复用所有权、CRUD、加密配置无关性和现有深链。来源关系第一阶段为一个知识页关联零或一个 Note；多来源专题留给后续专门变更。

### 2. 待整理是 Note 的只读投影，不复制历史数据

知识服务只把具有可读 `key_insight`、`conclusion` 或非空 `sections` 的 Note 投影为候选。只有原始文稿、空摘要或解析失败的 Note 继续留在视频资料库，不进入待整理。已通过 `source_note_id` 保存过的 Note 从待整理中排除。

候选保存端点从 Note 的标题、核心结论和 sections 生成知识页正文；重复保存返回已有页面，避免快速重复点击生成多条数据。AI sections 始终是草稿内容，不标记为已验证事实。

### 3. API 使用明确 view 参数并在数据库层分页

`GET /api/knowledge` 接受 `view=pages|inbox`。`pages` 查询 KnowledgeEntry；`inbox` 查询符合条件且未保存的 Note。两种视图独立搜索、计数和分页，不再把各 250 条候选拉到内存后混合。

响应统一提供 `kind`、`summary`、`status`、`origin`、`source_note_id` 和 `source_count`。历史 `kind=personal` 链接继续由前端识别，新的知识页链接使用 `kind=page`，候选使用 `kind=candidate`。

### 4. 桌面使用稳定主从阅读，移动端使用列表到详情

知识首页顶部只保留“新建知识页”和“去知萃研伴”；搜索与视图切换归入成果列表。桌面宽屏同时展示固定宽度成果列表与弹性阅读画布，点击行直接更新阅读内容，不再通过额外“概览”按钮触发布局跳变。移动端隐藏阅读画布，点击条目进入兼容详情路由。

正文采用编辑阅读优先的排版；视频封面仅作为来源缩略图。页面仅使用现有暖中性色和薄荷绿强调，不新增渐变、玻璃大面板或装饰动画。删除继续使用原生稳定 `<dialog>`，固定控件遵守安全区和最小触控面积。

宽屏不再在应用壳层内叠加第二个居中的固定宽度容器。页面只保留正常的外侧安全留白，主工作台占满其余宽度。搜索、知识页/待整理切换和结果数量都属于左侧列表控制区；右侧只承担当前条目的标题、核心内容与直接操作。阅读正文仍限制合理行长，但从左右分栏边界附近起排，而不是再次在右侧画布中居中，避免形成无意义的中间空洞。

列表行先展示标题和摘要，再展示类型与更新时间；不再把“手动整理”放在标题之前。canonical 页面不重复显示“已沉淀”，没有关联 Note 时不显示“0 个来源”。来源说明仅在真实存在时出现，视频来源操作与候选保存操作保持上下文相关。

桌面列表首页使用一条紧凑页面栏连接应用壳层与工作区，不再把标题、说明、圆角工作台分成三层容器。列表切换采用扁平标签，搜索与结果头直接属于列表栏。阅读区保持全高表面和独立滚动，但内部使用普通文档流：标题、正文与真实来源按稳定间距连续排列，短内容的剩余空白只出现在文档末尾，不得把正文垂直居中或把来源钉在视口底部。摘要与正文相同时只展示一次，并以“正文”等直接标签说明当前内容是什么，不补造状态、来源数量或教学卡片。

### 5. 旧视频知识详情降级为候选阅读，不复制完整视频工作区

旧 `/notes?id=<note>` 仍能打开候选摘要，但不再在知识页重复完整文稿、播放和四 Tab 工作区。用户通过“查看来源视频”进入 `/library/detail`；通过“去知萃研伴”进入现有 Agent 工作区。

## Risks / Trade-offs

桌面壳中的知识工作区使用明确的纵向 flex 高度链：应用主区占满视口，知识画布填充主区剩余空间，内部列表与阅读区再分别滚动。实现不得仅依赖从 `min-height` 继承的百分比高度，否则短内容会让工作区在窗口中部收缩并露出底层画布。

- [旧用户打开知识页后看到的数量骤减] → 用“待整理”承接已有有效视频摘要，并明确区分知识页与候选数量。
- [旧 KnowledgeEntry 缺少新增字段] → 启动迁移以可重复执行的列检查补齐字段，默认值保持旧数据可读。
- [SQLite 与 PostgreSQL 迁移语法不同] → 延续项目现有 `_migrate_db()` 方言分支，不引入 Alembic。
- [候选条件依赖历史 JSON 质量] → 服务层容错解析，并只在存在可读摘要内容时展示。
- [一个页面只能关联一个视频来源] → 第一阶段明确限制；多来源专题与冻结证据快照后续单独设计。
- [原创知识仍不能被 Agent 检索] → UI 只提供“去知萃研伴”，不使用“全部知识”文案。

## Migration Plan

1. 为 `knowledge_entries` 增加兼容字段和索引，旧行按 manual/canonical 读取。
2. 发布新的知识服务视图与候选保存 API，保留原有 CRUD 路由。
3. 发布新的 `/notes` 工作区和兼容详情路由。
4. 验证现有用户隔离、旧链接、服务端分页以及桌面/移动状态。
5. 回滚时前端可恢复旧视图；新增列与由用户保存的知识页保留，不影响旧 CRUD。

## Open Questions

- 多来源专题、Agent 回答持久化、Claim/Evidence 与版本历史留给后续变更，不阻塞本次发布。
