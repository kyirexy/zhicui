## Context

资料库前端已把 `sort` 传给后端，但界面只允许收藏切换排序，后端也只对收藏应用来源序号。喜欢和作品因此被统一强制成发布时间，且排序选择不会被持久化。侧栏提问入口同时使用了通用机器人图标，而项目已有统一的 `AgentMark`。

## Goals / Non-Goals

**Goals:**

- 让喜欢和收藏拥有一致、可预测且可持久化的排序体验。
- 保证作品始终按发布时间从新到旧排列。
- 复用现有来源序号与本地存储，不增加数据库迁移。
- 统一视频提问入口的品牌图形语言。

**Non-Goals:**

- 不改变抖音同步范围、视频提取或收藏/喜欢状态。
- 不新增服务端用户偏好表。
- 不为作品提供手动排序。

## Decisions

1. 使用现有 `collection | published` API 值表示“来源顺序”和“发布时间”。避免破坏 API；界面根据来源显示“最近喜欢”或“最近收藏”。
2. 后端仅对 `collect` 和 `like` 的 `collection` 排序应用 `source_rank`。作品不进入该分支；缺少 rank 的项目以发布时间作为稳定回退。
3. 使用现有 `useLocalStorage` 分别保存喜欢和收藏偏好。偏好值缺失或损坏时回退到来源顺序，避免为纯客户端设置增加服务端状态。
4. 提问入口复用 `AgentMark`，保留原链接、文案和交互范围，只简化图标容器。

## Risks / Trade-offs

- [旧的喜欢数据可能没有来源序号] → 下一次同步会补齐；在此之前后端按发布时间稳定回退。
- [本地偏好不会跨设备同步] → 这是显示偏好且符合本地优先设置策略，后续需要时再纳入用户设置同步。
- [复用 `collection` 枚举名称语义不够通用] → 保持 API 向后兼容，代码中通过动态文案明确真实含义。

## Migration Plan

先部署兼容的后端排序扩展，再部署前端控件与图标替换；两者均兼容旧客户端和旧数据。回滚只需恢复相关文件，无数据迁移。
